# Day 5. 계층형 아키텍처 — 심화 (경험자용)

## 1. 계층형 vs 육각형(포트-어댑터)

전통적 3계층은 위→아래 의존이지만, Service가 여전히 Repository **구현 기술**(MyBatis, JPA)에
간접적으로 묶입니다. **육각형 아키텍처**는 의존을 도메인 중심으로 뒤집습니다.

```
[웹 어댑터] → [입력 포트(UseCase 인터페이스)] → [도메인/서비스] → [출력 포트(Repository 인터페이스)] ← [영속성 어댑터(MyBatis)]
```

- 도메인·서비스는 어떤 프레임워크도 import 하지 않는다(순수 자바).
- `EmpRepository` 인터페이스는 **도메인 쪽에** 있고, MyBatis 구현은 바깥(어댑터)에서 그것을 구현.
- 이 과정은 학습 부담상 3계층으로 가되, `repository/` 를 인터페이스로 두는 것만으로도 "출력 포트"의
  절반은 얻습니다(Day 5 본문의 메모리 → MyBatis 교체가 그 증거).

## 2. 트랜잭션 스크립트 vs 도메인 모델

- **트랜잭션 스크립트**: 서비스 메서드 하나가 절차적으로 다 처리. MyBatis + 중소 규모에서 실용적.
  이 과정의 기본.
- **도메인 모델**: 규칙을 엔티티 메서드로. 복잡한 불변식이 많을 때. 서비스는 얇아지고 조율만.
- 섞어 쓰기: 대부분 트랜잭션 스크립트, "퇴사 처리"처럼 규칙이 뭉친 곳만 도메인 메서드(`emp.resign(date)`).

## 3. DTO 변환을 어디서 / 어떻게

- 위치: **Service 경계**. Controller는 `EmpForm`(웹 DTO)까지만, Repository는 `Emp`(도메인)까지만 안다.
- 수동 변환(정적 팩터리 `DeptListRow.from(dept, stats)`)이 가장 명시적이고 디버깅 쉽다.
- MapStruct(컴파일 타임 매퍼 생성)는 필드가 많을 때 유용하나, 규칙이 섞인 변환에는 오히려 불리.
- ModelMapper 같은 리플렉션 매퍼는 실수(필드명 우연 일치)와 성능 이슈로 지양.

## 4. 패키지 구조: 계층형 vs 기능형

```
계층형                          기능형(package-by-feature)
controller/ EmpController        emp/  EmpController, EmpService, EmpRepository
            DeptController       dept/ DeptController, DeptService, DeptRepository
service/    EmpService ...
repository/  ...
```

- 계층형: 학습·소규모에 명료(이 과정).
- 기능형: 한 기능을 고칠 때 파일이 한 폴더에 모여 있어 대규모에서 응집도가 높다. `emp` 패키지 밖에서
  `EmpRepository` 를 못 쓰게 접근 제한도 가능.
- 전환은 IDE 리팩터링으로 쉽다 — 처음엔 계층형, 커지면 기능형.

## 5. 순환 참조를 부르는 냄새

- `XxxService` 안에서 `YyyService` 를 호출하고, `Yyy` 도 `Xxx` 를 호출 → 공통 조회는 Repository로,
  공통 계산은 별도 도메인 서비스(`SalaryCalculator`)로.
- "편의상" 만든 God Service(`CommonService`) — 온갖 게 여기로 모이며 사이클 발생.
- 이벤트로 끊기: `empService.register()` 후 `publisher.publishEvent(new EmpRegistered(id))`,
  `@EventListener` 로 `deptService` 가 수신. 호출 대신 알림.

## 6. 컨트롤러를 얇게 유지하는 체크리스트

- `if` 문으로 업무 분기 → Service로.
- 여러 Service를 순서대로 호출하며 결과를 조합 → 그 조합 자체가 하나의 유즈케이스. Facade Service로.
- 응답 형태 가공(정렬·필터·페이지 계산) → Service가 `PageResult` 로 완성해서 반환.
- 예외 → try/catch를 컨트롤러마다 하지 말고 `@ControllerAdvice`(Day 14).

## 7. 인터페이스가 정말 하나뿐이면?

`EmpService` 인터페이스 + `EmpServiceImpl` 하나뿐이면 과하다는 의견이 있다(Day 4 심화).
이 과정의 절충: **Service는 인터페이스를 둔다**(교재 설명·테스트 대역·Day 9의 구현 교체 스토리에 유리),
**Controller는 인터페이스 없음**, **Repository는 Day 9부터 `@Mapper` 인터페이스가 곧 추상화**라
별도 인터페이스를 더 두지 않는다.
