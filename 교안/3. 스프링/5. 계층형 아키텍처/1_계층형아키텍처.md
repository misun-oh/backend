# Day 5. 계층형 아키텍처

| 항목 | 내용 |
|---|---|
| 선수학습 | Day 1(클래스 다이어그램·패키지 구조), Day 4(빈·DI·인터페이스) |
| 이번 챕터 | Controller/Service/Repository 역할 분리 → 인터페이스 기반 설계 → Day 1 설계를 **코드 뼈대**로 → 순환 참조 해결 |
| 권장 진행 | 1일 |
| 결과물 | `EmpController → EmpService → EmpRepository` 가 연결되고, 임시(in-memory) 저장소로 목록/등록이 되는 프로젝트 (DB는 Day 9) |

## 학습목표

- 요청 하나가 지나가는 3계층(Controller·Service·Repository)의 **책임 경계**를 말할 수 있다.
- Day 1에서 그린 클래스 다이어그램을 **패키지·클래스·인터페이스**로 옮길 수 있다.
- Service·Repository를 **인터페이스 + 구현**으로 나누고, 왜 그러는지 안다.
- DB 없이 **메모리 구현체**로 계층을 먼저 완성하고, 나중에 구현만 교체하는 흐름을 이해한다.
- 순환 참조가 왜 생기고 어떻게 푸는지 안다.

---

## 1. 3계층의 책임

Day 1에서 정리한 표를 다시 봅니다. 이번엔 실제 코드로 옮깁니다.

| 계층 | 애노테이션 | 한다 | 안 한다 |
|---|---|---|---|
| **Controller** | `@Controller` / `@RestController` | HTTP 파라미터·본문 받기, Service 호출, 화면 이름/응답 반환 | 업무 규칙, SQL, 트랜잭션 |
| **Service** | `@Service` | 검증 후 흐름 조립, **트랜잭션 경계**, DTO ↔ 도메인 변환, 여러 Repository 조합 | `HttpServletRequest` 참조, SQL 직접 작성 |
| **Repository** | `@Repository` | 저장/조회 한 단위, 결과를 객체로 매핑 | 업무 규칙, 화면 사정 |

의존 방향은 **위에서 아래로 한 방향**입니다: `Controller → Service → Repository`.
Repository가 Service를 부르거나, Service가 Controller를 부르면 안 됩니다.

```
요청 → Controller → Service → Repository → (DB)
응답 ←            ←         ←
```

## 3. 도메인과 DTO

```java
// domain/Emp.java
@Getter @Builder @AllArgsConstructor @NoArgsConstructor
public class Emp {
```

## 4. Repository — 인터페이스 + 메모리 구현

```java
// repository/EmpRepository.java
public interface EmpRepository {
    List<Emp> findAll();
    Optional<Emp> findById(Long id);
    Emp save(Emp emp);          // id 없으면 새로 부여, 있으면 갱신
    void deleteById(Long id);
}
```

```java
// repository/EmpMemoryRepository.java
@Repository
public class EmpMemoryRepository implements EmpRepository {

    private final Map<Long, Emp> store = new ConcurrentHashMap<>();
    private final AtomicLong seq = new AtomicLong(200);   // HR 스키마 사번대와 맞춤

    @Override public List<Emp> findAll() {
        return new ArrayList<>(store.values());
    }
    @Override public Optional<Emp> findById(Long id) {
        return Optional.ofNullable(store.get(id));
    }
    @Override public Emp save(Emp emp) {
        Long id = (emp.getEmpId() != null) ? emp.getEmpId() : seq.incrementAndGet();
        Emp toStore = Emp.builder()
                .empId(id).empName(emp.getEmpName()).email(emp.getEmpEmail())
                .deptId(emp.getDeptId()).salary(emp.getSalary())
                .hireDate(emp.getHireDate()).active(emp.isActive())
                .build();
        store.put(id, toStore);
        return toStore;
    }
    @Override public void deleteById(Long id) { store.remove(id); }
}
```

## 5. Service — 인터페이스 + 구현

```java
// service/EmpService.java
public interface EmpService {
    List<Emp> findAll();
    Emp get(Long id);
    Long register(EmpForm form);
    void modify(Long id, EmpForm form);
    void remove(Long id);
}
```

```java
// service/EmpServiceImpl.java
@Slf4j
@Service
@RequiredArgsConstructor
public class EmpServiceImpl implements EmpService {

    private final EmpRepository empRepository;   // 인터페이스에 의존

    @Override
    public List<Emp> findAll() {
        return empRepository.findAll();      // 부서명(deptName) 조인 채움은 Day 11
    }

    @Override
    public Emp get(Long id) {
        return empRepository.findById(id)
                .orElseThrow(() -> new NoSuchElementException("사원 없음: " + id));
    }

    @Override
    public Long register(EmpForm form) {
        Emp emp = Emp.builder()
                .empName(form.getEmpName()).email(form.getEmail())
                .deptId(form.getDeptId())
                .salary(form.getSalary() == null ? 0 : form.getSalary())
                .hireDate(form.getHireDate()).active(true)
                .build();
        Emp saved = empRepository.save(emp);
        log.info("사원 등록: empId={}", saved.getEmpId());
        return saved.getEmpId();
    }

    @Override
    public void modify(Long id, EmpForm form) {
        Emp cur = get(id);
        Emp updated = Emp.builder()
                .empId(cur.getEmpId())
                .empName(form.getEmpName()).email(form.getEmail())
                .deptId(form.getDeptId()).salary(form.getSalary())
                .hireDate(form.getHireDate()).active(cur.isActive())
                .build();
        empRepository.save(updated);
    }

    @Override
    public void remove(Long id) {
        get(id);                    // 없으면 예외
        empRepository.deleteById(id);
    }
}
```

> `@Transactional` 은 Day 13에서 붙입니다. 지금은 메모리라 트랜잭션 개념이 없습니다.

## 6. Controller — 얇게

```java
// controller/EmpController.java
@RestController
@RequestMapping("/api/emps")     // Thymeleaf 화면은 Day 8, 지금은 JSON으로 계층 확인
@RequiredArgsConstructor
public class EmpController {

    private final EmpService empService;

    @GetMapping
    public List<Emp> list() {
        return empService.findAll();
    }

    @GetMapping("/{id}")
    public Emp detail(@PathVariable Long id) {
        return empService.get(id);
    }

    @PostMapping
    public Map<String, Long> create(@RequestBody EmpForm form) {
        return Map.of("empId", empService.register(form));
    }

    @DeleteMapping("/{id}")
    public void delete(@PathVariable Long id) {
        empService.remove(id);
    }
}
```

확인:
```
POST /api/emps    {"empName":"신입","email":"a@b.com","deptId":5,"salary":2500000,"hireDate":"2026-09-01"}
GET  /api/emps
GET  /api/emps/201
```

**계층이 살아 있는지**가 핵심입니다. 나중에 Repository 구현을 MyBatis로 바꿔도(Day 9),
화면을 Thymeleaf로 바꿔도(Day 8) Service는 그대로입니다.

## 7. 순환 참조

`EmpService` 가 `DeptService` 를, `DeptService` 가 다시 `EmpService` 를 생성자 주입하면
부트 2.6+ 는 **기동을 실패**시킵니다.

```
The dependencies of some of the beans ... form a cycle:
  empServiceImpl → deptServiceImpl → empServiceImpl
```

푸는 법(우선순위):

1. **설계 재검토** — 대개 한 서비스가 너무 많은 일을 함. 공통 로직을 제3의 빈(`EmpDeptFacade`,
   또는 Repository 레벨 조회)으로 뺀다.
2. 한쪽을 **`ObjectProvider<T>`** 로 지연 조회 (`provider.getObject().xxx()`).
3. `@Lazy` 주입 (프록시로 미룸).
4. 이벤트(`ApplicationEventPublisher`)로 호출 대신 발행.

`allow-circular-references=true` 로 억지로 켜는 건 마지막 수단이자 냄새입니다.

## 자주 하는 실수

- **Controller에서 Repository 직접 호출** → Service를 건너뛰면 트랜잭션·검증·재사용이 깨진다.
- **도메인에 집계·화면상태값을 얹음** → 조인 컬럼(`deptName`)은 읽기 필드로 OK지만, 그 이상(선택여부·부서별 평균급여)은 전용 DTO로(Day 1).
- **Service 구현 클래스에 의존** → `private final EmpServiceImpl` 처럼. 인터페이스 `EmpService` 에 의존한다.
- **Repository에 업무 규칙** ("급여가 음수면 예외") → 규칙은 Service. Repository는 저장/조회만.
- **Service가 `HttpServletRequest`·`HttpSession` 을 받음** → 웹 기술이 Service로 새어 들어옴. 필요한 값만 파라미터로 넘긴다.

## 핵심 요약

| 계층 | 애노테이션 | 책임 | 의존 |
|---|---|---|---|
| Controller | `@RestController`/`@Controller` | 요청·응답 매핑 | → Service |
| Service | `@Service` | 업무 로직·트랜잭션·변환 | → Repository (인터페이스) |
| Repository | `@Repository` | 저장/조회 | → DB |

- Service·Repository는 **인터페이스 + 구현**. 구현만 바꿔 끼운다(메모리 → MyBatis, Day 9).
- 의존은 **한 방향**. 역방향/순환이 생기면 설계를 다시 본다.
