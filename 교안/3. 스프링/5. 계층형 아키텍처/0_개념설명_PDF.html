Day 5

계층형 아키텍처

Controller–Service–Repository — 역할을 나누고, 인터페이스로 갈아 끼우기

한 줄 요약 — 요청은 한 방향으로만 흐릅니다: Controller → Service → Repository → DB. 각 계층이 인터페이스에 의존하면, 구현체만 바꿔도 위·아래는 안 건드립니다(오늘은 메모리, Day 7엔 MyBatis).

1 3계층의 책임과 방향

  ctl -->|"호출"| svc["Service

  svc -->|"호출"| repo["Repository

저장 · 조회"]
  repo -->|"SQL"| db[("DB")]

계층애노테이션한다안 한다
Controller@Controller/@RestControllerHTTP 파라미터·본문 받기, Service 호출, 응답 반환업무 규칙, SQL, 트랜잭션
Service@Service검증 후 흐름 조립, 트랜잭션 경계, DTO↔도메인 변환HttpServletRequest 참조, SQL 직접 작성
Repository@Repository저장/조회 한 단위, 결과를 객체로 매핑업무 규칙, 화면 사정

오늘 (Day 5) — 메모리 구현

  • Map<Long, Emp> 로 임시 저장
  • DB 없이도 계층이 실제로 동작하는지 먼저 검증
  • 목적: "계층 분리가 잘 됐는지"에만 집중

Day 7 이후 — MyBatis 구현

  • EmpMapper + XML로 진짜 DB 접근
  • Service·Controller 코드는 한 줄도 안 바뀜
  • 이 "안 바뀜"이 계층형 아키텍처의 존재 이유

4 순환 참조 — 생기는 이유와 우선순위별 해법

flowchart LR
  A["EmpServiceImpl"] -->|"생성자 주입"| B["DeptServiceImpl"]
  B -->|"생성자 주입"| A
  A -. "서로가 서로를 필요로 함 → 기동 실패" .-> B
  1. 설계 재검토 — 공통 로직을 제3의 빈으로 분리 (가장 좋은 해법)

  4. 이벤트(ApplicationEventPublisher)로 호출 대신 발행

핵심만 다시

  • 의존 방향은 Controller → Service → Repository 한 방향뿐.
  • Service·Repository는 인터페이스 + 구현으로 나눠, 구현만 교체 가능하게.
  • 오늘은 메모리 구현 → Day 7에서 MyBatis로 교체해도 Service·Controller는 그대로.
  • 업무 규칙은 Service에만 — Controller·Repository에 새어 들어가지 않게.
  • 순환 참조는 대개 "한 서비스가 너무 많은 일을 한다"는 설계 신호.
