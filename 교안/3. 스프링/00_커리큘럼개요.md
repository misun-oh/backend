# Spring 교안 커리큘럼 개요 (20일 / 약 4주 과정)

이 교안은 **Java(OOP~DI 컨테이너 제작)** 와 **SQL(모델링~트랜잭션)** 을 마친 수강생이,
지금까지 손으로 만들던 것(수동 DI 컨테이너, JDBC DAO, 직접 짠 트랜잭션)을 **스프링이
어떻게 대신 해주는지** 배우고, 하나의 웹 애플리케이션을 완성하는 과정입니다.
영속성은 **MyBatis 중심**, 화면은 **Thymeleaf 서버 렌더링 중심**(후반부에 REST API),
인증은 **Spring Security 세션 로그인 → JWT** 순으로 편성합니다.

> **변경 이력**
> - 처음 계획(15일)에서 **로깅 설정·AOP**, **JUnit 테스트**(DB 연동 지점) 추가
> - **파일 업로드/다운로드**, **JWT 인증** 챕터 추가
> - **Day 1에 "사원관리 시스템 설계" 챕터 추가** — 유즈케이스·클래스·시퀀스 다이어그램으로
>   "무엇을, 어떤 화면으로, 어떻게 만들지" 먼저 그린다. 프로토타입은 `prototypes/templates/hr/`
> - **JPA는 이 과정에서 분리** — 연관관계·영속성 컨텍스트를 제대로 다루려면 별도 3~5일 과정으로 편성
> - 결과: **20일 / 약 4주**

## 이 과정을 관통하는 한 줄

> "부록3에서 리플렉션으로 `@Autowired`를 흉내 내는 DI 컨테이너를 직접 만들었고,
> JDBC로 `EmployeeDao`를 직접 짰습니다. 이제 그걸 스프링에게 맡깁니다."

## 새로 넣은·강화한 챕터 상세

### 사원관리 시스템 설계 (Day 1)
- **왜 먼저 설계인가**: 코드를 치기 전에 "어떤 화면이 필요하고, 각 화면이 어떤 흐름으로 이어지며, 클래스가 어떻게 나뉘는지"를 그려두면 이후 15일이 "그림을 코드로 옮기는" 과정이 된다.
- **요구사항 → 유즈케이스 다이어그램**: 액터(관리자/일반사용자), 유즈케이스(사원 목록 조회·검색, 사원 등록/수정/삭제, 부서 관리, 로그인). 기능 범위를 한 장으로 합의.
- **화면 목록 & 화면 흐름도**: 프로토타입 `prototypes/templates/hr/`(사원 목록·상세·등록폼·부서·대시보드 + 로그인 모달)을 기준으로, 어떤 버튼이 어느 화면으로 가는지 흐름도로 정리.
- **클래스 다이어그램**: `EmpController` → `EmpService` → `EmpMapper` 계층, 도메인(`Emp`, `Dept`)과 DTO(`EmpSearchCond`, `EmpForm`, `PageResult`, 집계용 `DeptListRow`)의 역할·관계.
- **시퀀스 다이어그램**: "사원 등록" 요청이 브라우저 → Controller → Service(`@Transactional`) → Mapper → DB 로 흐르고 응답이 되돌아오는 과정. "사원 목록 조회(검색·페이징)"도 한 장.
- **패키지 구조 확정**: `domain` / `dto` / `controller` / `service` / `mapper`(+ `resources/mapper/*.xml`) / `config` / `common`.
- **도구**: PlantUML 또는 Mermaid. 완벽한 UML보다 "팀이 같은 그림을 보는 것"이 목적.
- **실습**: 부서(Dept) 기능에 대해 유즈케이스·클래스·시퀀스 다이어그램을 직접 작성.

### 로깅 설정 (Day 3)
- **왜 로그인가**: `System.out.println` 디버깅의 문제 — 레벨 구분 불가, 한꺼번에 끄기 어려움, 시간·위치·스레드 정보 없음, 운영 서버에서 확인 불가
- **구조**: SLF4J(로깅 인터페이스) + Logback(스프링 부트 기본 구현체)
- **로그 레벨**: `TRACE < DEBUG < INFO < WARN < ERROR` — 각 레벨을 언제 쓰는지
- **설정**: `application.yml`의 `logging.level.*`(루트/패키지별), 콘솔 패턴, `logging.file.name`으로 파일 출력, 롤링 정책
- **사용법**: `@Slf4j`(Lombok) 또는 `LoggerFactory.getLogger(...)`, `log.info("회원 {} 로그인", id)` — 문자열 `+` 연결을 쓰지 않는 이유(성능·가독성)
- **환경 분리**: `logback-spring.xml` + `<springProfile>` 로 개발/운영 로그를 다르게

### AOP (Day 6)
- **횡단 관심사(cross-cutting concern)**: 로깅·트랜잭션·보안·성능 측정처럼 여러 계층/메서드에 반복되는 코드
- **Java 부록과의 연결**: 리플렉션으로 애노테이션을 읽어 처리했던 경험 → AOP는 **프록시**로 "메서드 호출 전후에 코드를 끼워 넣는" 것
- **용어**: Aspect, Advice(`@Before`/`@AfterReturning`/`@AfterThrowing`/`@Around`), Pointcut, JoinPoint, Proxy
- **작성**: `@Aspect` + `@Component`, 포인트컷 표현식(`execution(* com.example..service..*(..))`)
- **실습**: 서비스 메서드 실행 시간·파라미터·반환값을 자동으로 로그에 남기는 애스펙트
- **주의**: 스프링 AOP는 프록시 기반 → 같은 클래스 내부 메서드 호출에는 적용되지 않음
- **연결**: `@Transactional`, `@Cacheable`, Spring Security의 메서드 보안이 전부 AOP

### JUnit 테스트 (Day 10, DB 연동 직후)
- **JUnit이란**: 자바 표준 테스트 프레임워크(Spring Boot 4 기준 JUnit 6 / Jupiter). "코드가 의도대로 동작하는지 자동으로 검증하는 코드"
- **테스트하는 이유**:
  - 매번 화면 띄워 손으로 확인하는 반복 비용 제거
  - 코드를 고쳐도 기존 기능이 안 깨졌는지 즉시 확인(회귀 방지)
  - 리팩터링·라이브러리 교체의 안전망
  - 테스트 코드 자체가 "이 메서드는 이렇게 동작한다"는 문서
- **방법**: `@Test`, `Assertions.assertEquals`/`assertThat`/`assertThrows`, `@BeforeEach`/`@AfterEach`, given–when–then 구조, 테스트 클래스는 `src/test/java`에 `XxxTest`로
- **스프링 테스트**: `@SpringBootTest`로 컨테이너를 띄우고 빈 주입, Mapper/Service 테스트
- **DB 테스트**: 방금 만든 Mapper가 **진짜 DB에 붙어** `SELECT`/`INSERT`가 되는지 테스트로 확인 → 화면을 만들기 전에 데이터 계층부터 검증. `@Transactional`을 붙이면 테스트 후 자동 롤백되어 DB가 더럽혀지지 않음
- **실패 읽기**: 단언 실패 메시지(expected/actual)와 스택트레이스 읽는 법

### 파일 업로드와 다운로드 (Day 16)
- **업로드 기본**: `enctype="multipart/form-data"`, 컨트롤러의 `MultipartFile` 파라미터(폼·`@ModelAttribute` 혼합), `spring.servlet.multipart.max-file-size`/`max-request-size`
- **저장 전략**: 원본 파일명을 그대로 쓰면 위험(경로 조작·중복·한글) → **UUID로 리네임**, 저장 경로는 프로젝트 밖 디렉터리(`application.yml`로 설정), DB에는 원본명/저장명/크기/경로 등 **메타데이터만**
- **표시·다운로드**: 이미지 정적 매핑 또는 스트리밍, `ResponseEntity<Resource>` + `Content-Disposition: attachment`(한글 파일명 `filename*=UTF-8''` 인코딩)
- **검증**: 확장자 화이트리스트, MIME 타입, 용량 상한, 빈 파일 처리
- **연결**: Java `6.파일입출력`의 `Files`/스트림/`FileUploadExample`

### JWT 인증 (Day 19)
- **왜 JWT인가**: 세션 방식은 서버가 상태를 저장해야 함 → 수평 확장·SPA·모바일에서 부담. 토큰은 서버가 상태를 안 가짐(stateless)
- **구조**: `Header.Payload.Signature` — 서명(HMAC)으로 위변조 검증, `exp`로 만료, 클레임에 사용자/권한
- **흐름**: 로그인 성공 → 토큰 발급 → 클라이언트가 `Authorization: Bearer <token>` 로 전송 → 요청마다 서버가 서명·만료 검증 → 인증 객체 구성
- **구현**: 토큰 생성/파싱 유틸(`jjwt`), `OncePerRequestFilter` 로 검증 필터 작성, `SecurityContextHolder` 에 인증 주입, `SecurityFilterChain` 을 `STATELESS` 로
- **운영 이슈**: Access/Refresh 토큰 분리, 로그아웃·강제 만료(블랙리스트) 문제, 토큰 저장 위치(쿠키 vs 스토리지)와 XSS/CSRF
- **판단 기준**: 세션(서버 렌더링·단일 서버) vs JWT(REST·다중 클라이언트) 선택 가이드
