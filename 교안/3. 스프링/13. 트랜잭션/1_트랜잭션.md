# Day 13. 트랜잭션

| 항목 | 내용 |
|---|---|
| 선수학습 | SQL `8. TCL`(COMMIT/ROLLBACK), Day 9(CRUD) |
| 이번 챕터 | `@Transactional` 의 의미 → 커밋/롤백 규칙(체크·언체크 예외) → `readOnly` → 전파(propagation) 기초 → 프록시 한계(내부 호출) → 테스트로 롤백 검증 |
| 권장 진행 | 1일 |

## 학습목표

- SQL `8. TCL` 의 `COMMIT`/`ROLLBACK` 을 `@Transactional` 이 자동으로 해준다는 것을 안다.
- 기본 롤백 규칙(언체크 예외 → 롤백, 체크 예외 → 커밋)과 `rollbackFor` 를 안다.
- 조회 메서드에 `@Transactional(readOnly = true)` 를 붙이는 이유를 안다.
- 트랜잭션 경계를 **Service 메서드**에 두는 이유를 설명할 수 있다.
- `@Transactional` 이 AOP 프록시로 동작하므로 **같은 클래스 내부 호출**엔 안 걸린다는 것을 안다.
- 롤백을 테스트로 검증한다.

---

## 1. `@Transactional` 이 하는 일

SQL 과정에서 계좌 이체를 이렇게 했습니다.

```sql
START TRANSACTION;
UPDATE ACCOUNT SET BALANCE = BALANCE - 10000 WHERE ID = 1;   -- 출금
UPDATE ACCOUNT SET BALANCE = BALANCE + 10000 WHERE ID = 2;   -- 입금
COMMIT;   -- 둘 다 성공해야
```

스프링에서는 서비스 메서드에 애노테이션 하나면 됩니다.

```java
@Service
@RequiredArgsConstructor
public class TransferService {

    private final AccountMapper accountMapper;

    @Transactional
    public void transfer(Long from, Long to, int amount) {
        accountMapper.minusBalance(from, amount);   // 출금
        accountMapper.plusBalance(to, amount);      // 입금
        // 메서드가 정상 반환되면 → COMMIT
        // 도중에 RuntimeException 이 나면 → 자동 ROLLBACK (출금도 취소됨)
    }
}
```

- 메서드 **진입 시** 트랜잭션 시작(커넥션 확보), **정상 반환 시** 커밋, **예외 전파 시** 롤백.
- 이 전부를 스프링이 **AOP 프록시**로 감싸서 처리(Day 14). `@Transactional` 은 곧 트랜잭션 어드바이스.
- 부트는 `DataSourceTransactionManager` 를 자동 구성 — 별도 설정 불필요.

---

## 2. 롤백 규칙

**중요**: 기본값은 "**언체크(RuntimeException) 예외만 롤백**, 체크 예외는 커밋".

```java
@Transactional
public void a() {
    step1();
    throw new IllegalStateException("실패");   // RuntimeException → 롤백 O
}

@Transactional
public void b() throws IOException {
    step1();
    throw new IOException("실패");             // 체크 예외 → 기본은 커밋! (직관에 반함)
}
```

체크 예외에서도 롤백하려면 명시:
```java
@Transactional(rollbackFor = Exception.class)
public void b() throws IOException { ... }
```

특정 예외는 롤백 제외:
```java
@Transactional(noRollbackFor = NotFoundException.class)
```

> 실무에서는 대부분 **커스텀 예외를 `RuntimeException` 계열로** 만들어 이 문제를 피합니다
> (Day 15의 `@ControllerAdvice` 와도 잘 맞음).

## 3. `readOnly`

```java
@Transactional(readOnly = true)
public PageResult<Emp> search(EmpSearchCond cond) { ... }
```

- 조회 전용임을 명시. JDBC/드라이버·JPA에서 최적화 힌트(플러시 생략, 읽기 전용 커넥션 라우팅 등).
- MyBatis 단독에서는 성능 효과가 크진 않지만, **"이 메서드는 쓰지 않는다"는 의도**를 코드로 남기는 의미.

패턴: 클래스에 `@Transactional(readOnly = true)` 를 걸고, 쓰기 메서드에만 `@Transactional` 재정의.

```java
@Service
@Transactional(readOnly = true)      // 기본은 읽기 전용
@RequiredArgsConstructor
public class EmpServiceImpl implements EmpService {

    @Transactional                    // 이 메서드만 읽기/쓰기
    public Long register(EmpForm form) { ... }
}
```

## 4. 트랜잭션 경계 = Service

| 계층 | `@Transactional` |
|---|---|
| Controller | ✗ (웹 요청 처리만) |
| **Service** | **✓ (여기가 경계)** |
| Mapper | ✗ (SQL 한 번) |

이유:
- 하나의 **업무 단위**(사원 등록 = INSERT EMP + 첨부 저장 + 이력 기록)가 Service 메서드 하나.
- Mapper 하나하나에 트랜잭션을 걸면 "출금만 되고 입금 실패" 를 못 막는다.
- Controller에 걸면 뷰 렌더링·리다이렉트까지 트랜잭션에 들어가 커넥션을 오래 잡는다.

## 5. 프록시 한계 — 내부 호출 (Day 14 재확인)

```java
@Service
public class EmpServiceImpl {

    public void outer() {
        this.inner();          // ← 프록시를 안 거침
    }

    @Transactional
    public void inner() { ... }   // outer() 를 통해 들어오면 트랜잭션이 안 열린다!
}
```

- `outer()` 가 컨트롤러에서 호출되면 프록시를 거치지만, `outer()` 안에서 `this.inner()` 는
  **진짜 객체의 메서드를 직접** 부른다 → `inner()` 의 `@Transactional` 무시.
- 해결: `inner()` 를 **다른 빈**으로 분리하고 주입받아 호출. (또는 `@Transactional` 을 `outer()` 에.)

또 하나: `@Transactional` 은 **public 메서드**에만(프록시 기반). private/protected는 무시.

---

## 6. 전파(propagation) — 기초만

"트랜잭션 A가 진행 중인데 트랜잭션 메서드 B를 부르면?"

| 전파 옵션 | 동작 |
|---|---|
| `REQUIRED` (기본) | 진행 중 트랜잭션이 있으면 **참여**, 없으면 새로 시작 |
| `REQUIRES_NEW` | 항상 **새 트랜잭션** (기존 건 잠시 보류). "로그·이력은 본 작업이 롤백돼도 남긴다" |
| `NESTED` | 세이브포인트. 부분 롤백 |
| `SUPPORTS` / `NOT_SUPPORTED` / `NEVER` / `MANDATORY` | 상황별 |

대부분 `REQUIRED` 로 충분. "감사 로그는 무조건 남긴다" 같은 경우만 `REQUIRES_NEW`.
(단, `REQUIRES_NEW` 는 커넥션을 하나 더 쓰므로 남용 금지.)

## 7. 테스트로 롤백 검증

```java
@SpringBootTest
class EmpRegisterTxTest {

    @Autowired EmpService empService;
    @Autowired EmpMapper empMapper;

    @Test
    void 등록_도중_예외나면_아무것도_저장되지_않는다() {
        int before = empMapper.findAll().size();

        assertThatThrownBy(() ->
            empService.registerWithHistory(brokenForm())   // 중간에 RuntimeException
        ).isInstanceOf(RuntimeException.class);

        assertThat(empMapper.findAll()).hasSize(before);    // INSERT EMP 도 롤백됨
    }
}
```

> 이 테스트 클래스에는 `@Transactional` 을 **안** 붙입니다. 테스트가 트랜잭션을 감싸면
> `registerWithHistory` 내부 트랜잭션이 그 안에 참여해 버려, "서비스의 롤백"을 제대로 못 봅니다.
> 대신 테스트 후 데이터를 `@AfterEach` 로 직접 정리하거나, `@Sql` 로 초기화합니다.

## 8. 실습 사례 — Workbench에서 로그인 실패 카운트가 바로 안 보이는 경우

웹에서 로그인에 실패하면 다음 UPDATE가 실행된다고 가정합니다.

```sql
UPDATE EMP
SET login_fail_count = login_fail_count + 1,
    is_locked = CASE WHEN login_fail_count >= 4 THEN 1 ELSE 0 END
WHERE id = '201';
```

그런데 Workbench에서 다시 조회했을 때 카운트가 올라가지 않고, Workbench 세션을 끊었다가 다시 연결하면 변경된 값이 보일 수 있습니다.

### 8.1 원인 1: Workbench 세션의 미종료 트랜잭션

Workbench에서 `autocommit = 0`인 상태로 먼저 SELECT를 실행하면 해당 세션에 트랜잭션과 조회 스냅샷이 만들어질 수 있다.
그 뒤 웹 애플리케이션이 다른 커넥션에서 UPDATE와 COMMIT을 해도, 기존 Workbench 세션은 이전 스냅샷을 계속 볼 수 있다.

```text
Workbench 세션 A에서 SELECT 실행
→ 조회 스냅샷 생성
→ 웹 애플리케이션이 UPDATE 후 COMMIT
→ 세션 A에서 다시 SELECT
→ 이전 값이 보일 수 있음
→ Workbench 재접속
→ 새 세션에서 최신 값 확인
```

이 경우 애플리케이션의 커밋이 늦은 것이 아니라 Workbench가 이전 트랜잭션 상태를 보고 있는 것이다.

현재 세션 상태 확인:

```sql
SELECT
    CONNECTION_ID(),
    DATABASE(),
    USER(),
    @@autocommit,
    @@in_transaction,
    @@transaction_isolation;
```

조회 세션을 끝내고 최신 값을 다시 보려면:

```sql
COMMIT;
-- 또는 조회만 했고 변경사항이 없다면
ROLLBACK;

SELECT id, login_fail_count, is_locked
FROM EMP
WHERE id = '201';
```

실습 조회용 Workbench는 다음처럼 autocommit을 켜 두는 것이 혼동이 적다.

```sql
SET SESSION autocommit = 1;
```

### 8.2 원인 2: 애플리케이션에 트랜잭션 경계가 없는 경우

애플리케이션의 DataSource가 `autocommit = false`인데 Service 메서드에 `@Transactional`이 없으면, Mapper가 실행한 UPDATE의 커밋 시점이 보장되지 않는다.
커넥션 풀에 반환되는 과정에서 롤백되어 변경이 사라질 수도 있다.

로그인 실패 카운트처럼 반드시 남겨야 하는 변경은 Service에 트랜잭션 경계를 둔다.

```java
@Transactional(propagation = Propagation.REQUIRES_NEW)
public int updateFailCount(String id) {
    return mapper.updateFailCount(id);
}
```

`REQUIRES_NEW`는 로그인 검증 흐름과 실패 카운트 저장을 별도 트랜잭션으로 분리한다. 카운트 UPDATE가 정상 종료되면 커밋되고, UPDATE 중 예외가 발생하면 해당 변경만 롤백된다.

### 8.3 Workbench 버전 문제가 아닌지 확인하는 방법

Workbench 버전보다 다음 접속 정보와 트랜잭션 상태가 더 중요하다.

```sql
SELECT DATABASE(), USER(), @@hostname, @@port, @@autocommit;
```

애플리케이션 로그에서도 UPDATE 결과 행 수를 확인한다.

```java
int result = service.updateFailCount(id);
System.out.println("updateFailCount result = " + result);
```

| 결과 | 확인할 내용 |
|---|---|
| `result = 0` | 아이디가 없거나 애플리케이션과 Workbench가 다른 DB를 보고 있음 |
| `result = 1`, 새 세션에서 보임 | 기존 Workbench 세션의 트랜잭션 스냅샷 문제 |
| `result = 1`, 새 세션에서도 안 보임 | 애플리케이션 커밋 설정, DB 계정, 테이블 컬럼 확인 |

> 결론: Workbench에서 `COMMIT` 또는 `ROLLBACK` 후 다시 조회하고, 애플리케이션의 변경 작업은 Service의 `@Transactional`로 커밋·롤백을 명확히 관리한다.

## 자주 하는 실수

- **체크 예외인데 롤백을 기대** → 기본은 커밋. `rollbackFor = Exception.class` 또는 커스텀 런타임 예외.
- **`@Transactional` 을 같은 클래스 내부에서 호출** → 안 걸림. 별도 빈으로 분리.
- **`@Transactional` 을 private 메서드에** → 무시됨. public.
- **트랜잭션 안에서 외부 API 호출·파일 IO·`Thread.sleep`** → 커넥션을 오래 잡아 풀 고갈. 트랜잭션은 짧게.
- **Controller에 `@Transactional`** → 렌더링까지 트랜잭션. Service에.
- **예외를 잡아서 로그만 찍고 삼킴** → 예외가 프록시까지 전파 안 돼 **롤백이 안 된다**. 다시 던지거나
  `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`.
- **`@Transactional` 인데 트랜잭션 매니저가 없음**(순수 web만) → MyBatis/jdbc 스타터가 있어야 자동 구성.

## 핵심 요약

| 요소 | 내용 |
|---|---|
| `@Transactional` | 메서드 진입 시 begin, 정상 반환 시 commit, 예외 전파 시 rollback (AOP 프록시) |
| 롤백 규칙 | 언체크(RuntimeException) → 롤백 / 체크 예외 → 커밋. `rollbackFor` 로 확장 |
| `readOnly = true` | 조회 전용 표시(+최적화 힌트) |
| 경계 | **Service 메서드**. Controller·Mapper엔 안 붙임 |
| 프록시 한계 | 내부 호출·private 미적용 |
| 전파 | 기본 `REQUIRED`. 이력 등 예외적으로 `REQUIRES_NEW` |
| 주의 | 트랜잭션 안에서 느린 작업 금지, 예외 삼키면 롤백 안 됨 |
