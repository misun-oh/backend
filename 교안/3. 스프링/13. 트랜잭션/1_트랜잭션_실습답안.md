## 문제 2. 롤백되는 등록

```java
@Transactional
public Long registerWithHistory(EmpForm form) {
    Emp emp = toEmp(form);
    empMapper.insert(emp);                       // 1) 사원 저장
    if (true) throw new IllegalStateException("이력 저장 실패");   // 2) 예외
    // historyMapper.insert(...);
    return emp.getEmpId();
}
```

테스트(테스트에 `@Transactional` 없음):
```java
@SpringBootTest
class RegisterTxTest {
    @Autowired EmpService empService;
    @Autowired EmpMapper empMapper;
    Long createdId;

    @AfterEach void clean() { if (createdId != null) empMapper.deleteById(createdId); }

    @Test void 트랜잭션이면_롤백() {
        int before = empMapper.findAll().size();
        assertThatThrownBy(() -> empService.registerWithHistory(form(901L)))
                .isInstanceOf(RuntimeException.class);
        assertThat(empMapper.findAll()).hasSize(before);   // 롤백 → 그대로
    }
}
```

`@Transactional` 을 떼면: `empMapper.insert` 는 각자 커밋되므로 예외 후에도 **사원 901이 남는다**
→ `before + 1`. (부분 반영 = 데이터 정합성 깨짐)

## 문제 3. 체크 예외의 함정

```java
@Transactional
public void registerAndExport(EmpForm form) throws IOException {
    empMapper.insert(toEmp(form));
    throw new IOException("파일 실패");     // 체크 예외
}
```

**확인**: 사원이 **저장돼 있다(커밋됨).** `@Transactional` 의 기본 롤백 규칙은
"언체크(RuntimeException)만 롤백, 체크 예외는 커밋"이기 때문.

**고치는 법 2가지**

1. `@Transactional(rollbackFor = Exception.class)` — 체크 예외도 롤백.
2. `IOException` 을 잡아 `throw new RuntimeException("파일 실패", e)` — 언체크로 변환해 던짐
   (실무에서 커스텀 예외를 런타임 계열로 만드는 이유).

## 문제 4. 내부 호출 한계

```java
public void bulkRegister(List<EmpForm> forms) {
    for (EmpForm f : forms) this.registerOne(f);   // this. → 프록시 미경유
}
@Transactional
public void registerOne(EmpForm f) { ... }
```

- `bulkRegister` 자체에 트랜잭션이 없고, `this.registerOne(f)` 는 **프록시를 안 거치므로**
  `registerOne` 의 `@Transactional` 도 **동작하지 않는다** → 각 INSERT가 그냥 auto-commit.
- 3번째에서 예외가 나면 앞의 2건은 이미 커밋되어 남고, 3번째만 실패.

**해결**
- 원자성이 필요하면 `bulkRegister` 에 `@Transactional` (전부 성공 or 전부 롤백).
- "실패 건만 건너뛰기"가 목적이면 `registerOne` 을 **다른 빈**(`EmpRegistrar`)으로 분리하고
  주입받아 호출 → 각 호출이 프록시를 거쳐 개별 트랜잭션(`REQUIRES_NEW`)을 갖게.

## 문제 5. 예외를 삼키면

```java
@Transactional
public void x() {
    aMapper.insert(...);
    try { bMapper.insert(...); } catch (Exception e) { log.error("b 실패", e); }
}
```

- `a` 는 **커밋된다.** 예외를 메서드 밖으로 던지지 않으면 트랜잭션 어드바이스(프록시)는 정상 종료로
  보고 커밋한다. (단, `bMapper.insert` 실패가 DB 제약 위반이었다면 그 statement만 실패했을 뿐
  트랜잭션은 살아 있음 — MyBatis 단독 기준.)
- 주의: 만약 `b` 실패가 트랜잭션을 `rollback-only` 로 만들었다면(중첩 트랜잭션·JPA 등), 삼켜도
  최종 커밋 시 `UnexpectedRollbackException`.

**"a는 살리고 b만 건너뛰기"**
- `b` 를 별도 빈 + `@Transactional(propagation = REQUIRES_NEW)` 로 분리 → `b` 만의 트랜잭션이
  독립적으로 커밋/롤백. `x` 는 `b` 호출을 try/catch 로 감싸 실패해도 진행.
- 또는 `b` 를 트랜잭션 커밋 이후(`AFTER_COMMIT` 이벤트)로 미룸 — `b` 가 부가 작업이면.
