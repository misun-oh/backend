# Day 2. 스프링 부트 시작 — 심화 (경험자용)

본문은 "프로젝트 만들고 첫 요청 처리"까지였습니다. 여기서는 그 밑에서 벌어지는 일을 봅니다.

## 1. 웹 애플리케이션은 어떻게 '웹'이 되는가 — starter-web 과 DispatcherServlet

`@RestController` 를 만들고 `@GetMapping` 을 달아도, 프로젝트에 **웹 스타터가 없으면 그 메서드는 절대 호출되지 않습니다.** 부트 로그는 잠깐 뜨다가 앱이 그냥 종료됩니다. 왜 그런지 봅니다.

### 1.1 `@Controller` / `@RestController` 는 '표식'일 뿐

- `@Controller` = `@Component` + "나는 웹 핸들러다"라는 메타데이터. 스프링은 이걸 보고 **빈만 등록**합니다.
- `@GetMapping` · `@RequestMapping` 도 그 자체로는 아무 일도 안 합니다. 누군가 이 애노테이션을 **읽어서** `URL + HTTP메서드 → 자바 메서드` 표를 만들어야 의미가 생깁니다.
- 그 "누군가" = `RequestMappingHandlerMapping` / `RequestMappingHandlerAdapter`, 그리고 요청을 받아 이들에게 넘기는 **`DispatcherServlet`**. 전부 `spring-webmvc` 에 들어 있고, 애플리케이션이 **웹 앱으로 떠야** 자동 등록됩니다.

### 1.2 웹 스타터가 실제로 넣어주는 것

`spring-boot-starter-webmvc`(부트 4, 구 `starter-web`):

| 구성요소 | 역할 |
|---|---|
| 내장 Tomcat (`spring-boot-starter-tomcat`) | HTTP 를 실제로 수신하는 서버 |
| `spring-webmvc` (`DispatcherServlet`, `RequestMappingHandlerMapping`/`Adapter`) | URL → 핸들러 메서드 연결·실행 |
| Jackson | 객체 ↔ JSON |
| 자동 구성 (`ServletWebServerFactoryAutoConfiguration`, `DispatcherServletAutoConfiguration`, `WebMvcAutoConfiguration`) | 위 셋을 조립 |

> 주의: `spring-boot-starter-thymeleaf` 는 `spring-web` 만 딸려올 뿐 **`spring-webmvc`·내장 톰캣은 가져오지 않습니다.** 즉 thymeleaf 스타터만으로는 웹 앱이 안 됩니다. (Spring Initializr 에서 Thymeleaf 를 고르면 Web 도 같이 넣어줄 뿐입니다.) 우리 `build.gradle` 에는 `spring-boot-starter-webmvc` 가 별도로 들어 있습니다.

### 1.3 스프링 부트는 어떻게 '웹 앱'이라고 판단하나 — `WebApplicationType`

`SpringApplication` 이 뜰 때 **클래스패스만 보고** 종류를 정합니다.

```java
// SpringApplication 생성자
this.webApplicationType = WebApplicationType.deduceFromClasspath();
```

| 클래스패스에 있는 것 | 판정 | 만드는 컨텍스트 | 내장 서버 |
|---|---|---|---|
| `DispatcherServlet` + `jakarta.servlet.Servlet` | `SERVLET` | `…ServletWebServerApplicationContext` | **뜬다** |
| `webflux` 계열만 | `REACTIVE` | `…ReactiveWebServerApplicationContext` | 뜬다(Netty) |
| 둘 다 없음 | `NONE` | `AnnotationConfigApplicationContext` | **안 뜬다** |

`NONE` 이면 `run()` 이 **컨텍스트 초기화만 하고 즉시 리턴** → `main` 종료 → 프로세스 끝. 이게 "Started App 로그 직후 그냥 꺼진다"는 증상의 정체입니다.

강제 지정도 가능합니다(웹 스타터가 있어도 서버를 안 띄우고 싶을 때):

```java
new SpringApplicationBuilder(HrApplication.class)
    .web(WebApplicationType.NONE)   // 배치·CLI 성 앱
    .run(args);
```

### 1.4 자동 구성이 '조건부'라서 통째로 꺼진다

웹 관련 자동 구성 클래스들은 전부 조건(`@Conditional`)이 걸려 있습니다.

```java
@AutoConfiguration
@ConditionalOnClass({ Servlet.class, DispatcherServlet.class })   // 이 클래스가 클래스패스에 있을 때만
@ConditionalOnWebApplication(type = SERVLET)                      // 서블릿 웹 앱일 때만
public class DispatcherServletAutoConfiguration { ... }
```

| 자동 구성 | 하는 일 | 켜지는 조건 |
|---|---|---|
| `ServletWebServerFactoryAutoConfiguration` | 내장 톰캣 기동 | 톰캣 클래스 존재 + 웹 앱 |
| `DispatcherServletAutoConfiguration` | `DispatcherServlet` 등록·매핑 | `DispatcherServlet` 클래스 존재 |
| `WebMvcAutoConfiguration` | `HandlerMapping`/`Adapter`, 메시지 컨버터, 뷰 리졸버, 정적 리소스 | 웹 앱 + 사용자가 직접 `WebMvcConfigurationSupport` 등록 안 함 |

웹 스타터가 없으면 `DispatcherServlet` **클래스 자체가 클래스패스에 없어서** 이 셋이 전부 **Negative match** → 컨트롤러 빈은 컨텍스트에 있어도 요청을 받아 넘겨줄 통로가 없습니다.

### 1.5 요청 하나가 컨트롤러 메서드까지 오는 순서 (웹 앱일 때)

1. 내장 톰캣이 `TCP:8080` 에서 HTTP 요청 수신
2. **`DispatcherServlet`** 이 받음 (프론트 컨트롤러 — 모든 요청의 입구)
3. `HandlerMapping` 이 `URL + 메서드` 로 핸들러(= 우리 컨트롤러 메서드)를 찾음
4. `HandlerAdapter` 가 인자 바인딩(`@PathVariable` · `@RequestParam` · `@RequestBody` …) 후 메서드 호출
5. 리턴값 처리
   - `@ResponseBody` / `@RestController` → `HttpMessageConverter`(Jackson)가 JSON 으로 직렬화
   - 뷰 이름(String) → `ViewResolver` 가 템플릿 찾아 렌더링 (Thymeleaf)
6. 완성된 응답을 톰캣이 클라이언트로 반환

`@Controller` 는 **3~5 단계에서만** 의미가 있습니다. 그 앞의 1~2(서버·DispatcherServlet)가 없으면 3부터가 시작되지 않습니다.

### 1.6 증상과 확인 방법

- **증상**: `Tomcat started on port 8080` 로그가 없다 / `Started HrApplication in ...` 직후 프로세스 종료 / 브라우저는 "연결 거부".
- **확인**
  - `build.gradle` 에 `spring-boot-starter-webmvc`(또는 3.x 이름 `-web`)가 있는지. `-thymeleaf` 만으로는 안 됨(1.2).
  - `--debug` 로 실행 → `CONDITIONS EVALUATION REPORT` 에서 `DispatcherServletAutoConfiguration` 이 **Positive matches** 에 있는지 (없으면 왜 빠졌는지 이유도 출력됨).
  - `main` 에서 `.web(WebApplicationType.NONE)` 으로 강제하고 있지 않은지.

> 배포 형태(jar/war, 톰캣 교체, WebFlux)는 5절에서 이어집니다.

### 1.7 빈으로 등록하는 객체 vs 등록하지 않는 객체 — DTO는 왜 컨테이너 밖에 있나

1.1에서 "`@Controller` = `@Component` + 표식, 스프링은 이걸 보고 **빈만 등록**한다"고 했습니다.
그런데 본문에서 계속 만든 `EmpSearchCond`, `EmpCreateRequest` 같은 DTO 는 `@Component` 를 붙인
적이 없습니다. 왜 어떤 객체는 빈으로 등록하고, 어떤 객체는 그냥 `new` 해서 쓰는지 정리합니다.

#### 판단 기준: "로직을 하는가" vs "값을 담을 뿐인가"

| | 빈(bean)으로 등록 | 빈으로 등록하지 않음 (DTO 등) |
|---|---|---|
| 대표 예 | `EmpController`, `EmpService`, `EmpMapper` | `EmpSearchCond`, `EmpCreateRequest`, `EmpListRow` |
| 하는 일 | 로직 수행 — 요청 처리, 계산, 조회·저장 | 값을 담아 옮기는 그릇(데이터) |
| 생성 시점 | 컨테이너가 뜰 때 **딱 한 번** (기본 싱글톤) | 필요할 때마다, **요청마다** 새로 |
| 인스턴스 수 | 애플리케이션 전체에서 보통 1개 | 요청 수만큼(동시 사용자 수만큼) 여러 개 |
| 상태(필드) | 보통 **무상태** — 필드는 주입받은 다른 빈에 대한 참조뿐 (`EmpService` 안의 `EmpMapper` 등) | **상태 그 자체** — 필드에 이번 요청의 실제 데이터가 들어 있음 |
| 붙는 애노테이션 | `@Component`/`@Service`/`@Repository`/`@Controller`/`@RestController`, 또는 `@Configuration` 의 `@Bean` 메서드 | 없음. 평범한 자바 클래스(POJO) |
| 누가 만드나 | `@ComponentScan` 이 찾아서 컨테이너가 생성·보관·주입 | 우리가 직접 `new`, 또는 스프링이 요청마다 임시로 `new` 해서 값만 채움(아래 "커맨드 객체 바인딩과의 연결" 참고) |

#### DTO 를 빈으로 등록하면 왜 위험한가

`EmpSearchCond` 에 실수로 `@Component` 를 붙였다고 해 봅시다. 그러면 스프링이 이 클래스를
**컨테이너에 딱 하나만 만들어서(싱글톤) 모든 요청이 그 하나를 공유**하게 됩니다.

```java
@Component   // 절대 이렇게 하면 안 됨
public class EmpSearchCond {
    private String keyword;
    // ...
}
```

- 사용자 A 가 `keyword=김` 으로 검색하는 동시에 사용자 B 가 `keyword=이` 로 검색하면, **같은 객체의
  같은 필드**에 두 값이 번갈아 덮어써집니다 — A 의 검색 결과에 B 의 조건이 섞이는 **동시성 버그**입니다.
- 컨트롤러(`EmpController`)나 서비스(`EmpService`)는 이런 문제가 없는 이유: 이들은 **자기 자신의
  데이터를 필드에 담아두지 않고**, 메서드가 호출될 때마다 넘어온 매개변수(`cond`, `id` 등)만
  가지고 일하기 때문입니다. 그래서 여러 요청이 **같은 인스턴스를 동시에 써도 안전**합니다(무상태).
- 반대로 DTO 는 "이번 한 번의 요청·응답에 실린 값" 그 자체이므로, 요청마다 **독립된 인스턴스**여야
  합니다. 그래서 빈으로 등록하지 않고, 필요할 때마다 새로 만듭니다.

#### 커맨드 객체 바인딩과의 연결

`2_컨트롤러.md` 2.3절(파라미터 자동수집)에서 본 `@ModelAttribute EmpSearchCond cond` 를 다시
보면: 스프링은 이 메서드가 호출될 때마다 `new EmpSearchCond()` 를 하고, 쿼리스트링 값을
`setXxx()` 로 채운 뒤 매개변수로 넘겨줄 뿐입니다 — **컨테이너에 등록해서 재사용하는 게 아니라,
매번 새로 만들었다가 요청 처리가 끝나면 버려집니다.** `@RequestBody` 로 JSON 을 객체로 받을
때도 마찬가지로, Jackson 이 매 요청마다 새 인스턴스를 만듭니다.

> **한 줄 요약**: "여러 요청이 동시에 같이 써도 되는, 로직만 있는 객체" → 빈(`@Component` 계열).
> "요청 하나하나가 자기만의 값을 담아야 하는 객체" → 빈이 아닌 일반 객체(DTO·Entity·VO). Day 4
> (IoC/DI)에서 싱글톤 스코프와 빈 생명주기를 더 깊이 다룹니다.

## 2. 자동 구성(auto-configuration)은 어떻게 동작하나

`@EnableAutoConfiguration` 은 클래스패스의
`META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`
파일에 적힌 **자동 구성 클래스 목록**을 읽어옵니다(부트 2.7 이전엔 `spring.factories`).

각 자동 구성 클래스는 **조건(@Conditional)** 을 달고 있어, 조건이 맞을 때만 빈을 등록합니다.

```java
@AutoConfiguration
@ConditionalOnClass(DispatcherServlet.class)          // 클래스패스에 이 클래스가 있을 때만
@ConditionalOnWebApplication(type = SERVLET)
public class DispatcherServletAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean(DispatcherServlet.class) // 사용자가 직접 등록 안 했을 때만
    public DispatcherServlet dispatcherServlet(...) { ... }
}
```

핵심 조건 애노테이션:

| 애노테이션 | 의미 |
|---|---|
| `@ConditionalOnClass` / `@ConditionalOnMissingClass` | 특정 클래스가 클래스패스에 있냐/없냐 |
| `@ConditionalOnBean` / `@ConditionalOnMissingBean` | 특정 빈이 이미 등록됐냐/아니냐 (사용자 정의가 우선) |
| `@ConditionalOnProperty` | `application.yml` 의 특정 값이 설정됐냐 |
| `@ConditionalOnWebApplication` | 서블릿/리액티브 웹 앱이냐 |

**무엇이 켜지고 꺼졌는지 확인**: 실행 인자에 `--debug` 를 주면 콘솔에
`CONDITIONS EVALUATION REPORT`(Positive/Negative matches)가 출력됩니다. 또는
`spring-boot-starter-actuator` + `/actuator/conditions`.

**특정 자동 구성 끄기**:
```java
@SpringBootApplication(exclude = { DataSourceAutoConfiguration.class })
```

## 3. 의존성 버전은 누가 정하나 — BOM

`build.gradle` 상단:
```groovy
plugins {
    id 'org.springframework.boot' version '4.0.x'
    id 'io.spring.dependency-management' version '1.1.x'
}
```

`io.spring.dependency-management` 가 `spring-boot-dependencies` **BOM**(Bill of Materials)을 적용합니다.
그래서 `implementation 'org.springframework.boot:spring-boot-starter-webmvc'` 처럼 **버전을 안 써도**
BOM에 정의된, 서로 호환이 검증된 버전이 적용됩니다.

특정 라이브러리 버전을 강제로 올리려면 (Boot 4는 Jackson **3** 기준):
```groovy
ext['jackson-bom.version'] = '3.0.x'       // BOM이 노출하는 프로퍼티 override
// 또는
dependencies { implementation 'tools.jackson.core:jackson-databind:3.0.x' }
```

## 4. `SpringApplication` 커스터마이징

```java
public static void main(String[] args) {
    SpringApplication app = new SpringApplication(HrApplication.class);
    app.setBannerMode(Banner.Mode.OFF);                    // 배너 끄기
    app.setDefaultProperties(Map.of("server.port", "8081"));
    app.addListeners(new MyStartupListener());
    app.run(args);
}
```

앱 기동 직후 코드를 한 번 실행하려면 `ApplicationRunner` / `CommandLineRunner` 빈:

```java
@Bean
CommandLineRunner init(EmpService empService) {
    return args -> log.info("기동 완료. 사원 수 = {}", empService.count());
}
```

둘 다 컨테이너 준비 후, 톰캣이 요청을 받기 직전에 실행됩니다. `@Order` 로 순서를 줄 수 있습니다.

## 5. 내장 톰캣 vs 외부 WAS, jar vs war

- 기본은 **jar + 내장 톰캣**. `java -jar hr.jar` 로 어디서나 실행 → 컨테이너 이미지·클라우드에 유리.
- 굳이 외부 톰캣에 배포해야 하면: `war` 패키징 + `SpringBootServletInitializer` 상속 +
  `providedRuntime 'org.springframework.boot:spring-boot-starter-tomcat'`.
- 톰캣 대신 Undertow/Jetty로 교체: `starter-webmvc` 에서 `spring-boot-starter-tomcat` 을 exclude 하고
  `spring-boot-starter-undertow` 추가.
- 논블로킹이 필요하면 `spring-boot-starter-webflux`(이 과정은 서블릿 MVC).

## 6. 실행 가능 jar(fat jar)의 구조

`./gradlew bootJar` 로 만든 jar 를 풀어 보면:

```
hr.jar
├── META-INF/MANIFEST.MF        Main-Class: org.springframework.boot.loader.JarLauncher
├── org/springframework/boot/loader/...   (부트 로더)
└── BOOT-INF
    ├── classes/                우리 클래스 + resources
    └── lib/                     의존 jar 들 (jar 안의 jar)
```

`java -jar` 하면 `JarLauncher` 가 먼저 뜨고, 중첩 jar 를 읽는 커스텀 클래스로더로 우리 `main` 을 호출합니다.
일반 `java -cp` 로는 중첩 jar 를 못 읽습니다.

## 7. 프로파일로 환경 나누기

```
application.yml            공통
application-dev.yml        개발용 (H2, 로그 DEBUG …)
application-prod.yml       운영용 (실DB, 로그 WARN …)
```

활성화:
```bash
java -jar hr.jar --spring.profiles.active=prod
# 또는 환경변수 SPRING_PROFILES_ACTIVE=prod
```

한 파일 안에서 나누는 문법(부트 2.4+):
```yaml
spring:
  config:
    activate:
      on-profile: dev
server:
  port: 8080
---
spring:
  config:
    activate:
      on-profile: prod
server:
  port: 80
```

빈에도 프로파일을 걸 수 있습니다: `@Profile("dev")`.

## 8. Actuator (운영 점검 엔드포인트)

```groovy
implementation 'org.springframework.boot:spring-boot-starter-actuator'
```
```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info,conditions,env,loggers
```
- `/actuator/health` — 헬스 체크(로드밸런서·쿠버네티스가 사용)
- `/actuator/conditions` — 자동 구성 매칭 리포트
- `/actuator/loggers` — 런타임에 로그 레벨 변경 (Day 3와 연결)
- 운영에서는 노출 범위·인증(Spring Security)에 반드시 신경 쓸 것.

## 9. 시작 시간 줄이기 (참고)

- `spring.main.lazy-initialization=true` — 빈을 처음 쓸 때 생성(개발 편의, 운영은 주의).
- AOT + GraalVM 네이티브 이미지(`bootBuildImage`, `native` 프로파일) — 밀리초 단위 기동, 빌드 복잡도 상승.
- 불필요한 스타터 제거가 가장 확실.
