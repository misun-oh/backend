# Day 14. 검증과 예외 처리

| 항목 | 내용 |
|---|---|
| 선수학습 | Day 7(폼 바인딩), Day 8(Thymeleaf), Day 13(예외·롤백) |
| 이번 챕터 | Bean Validation(`@NotBlank`·`@Size`·`@Email`·`@Pattern`) → `@Valid` + `BindingResult` → Thymeleaf 에러 표시 → 커스텀 검증 → `@ControllerAdvice`/`@ExceptionHandler` → 에러 페이지 |
| 권장 진행 | 1일 |
| 의존성 | `implementation 'org.springframework.boot:spring-boot-starter-validation'` |
| 결과물 | 프로토타입(`emp-form.html`)의 빨간 에러 메시지가 실제로 동작. 전역 예외가 일관된 화면/응답으로 |

## 학습목표

- DTO 필드에 검증 애노테이션을 붙이고 `@Valid` + `BindingResult` 로 컨트롤러에서 처리한다.
- Thymeleaf `th:errors`, `th:errorclass`, `#fields.hasErrors()` 로 에러를 화면에 표시한다.
- 필드 단독으로 안 되는 규칙(이메일 중복, 두 필드 관계)을 커스텀 검증으로 만든다.
- `@RestControllerAdvice` / `@ExceptionHandler` 로 예외를 한곳에서 처리한다.
- 404·500 에러 페이지를 커스터마이징한다.

## 1. Bean Validation — DTO에 규칙 달기

```java
// dto/EmpForm.java
@Getter @Setter
public class EmpForm {

    private Long empId;   // 수정 시 채워짐

    @NotBlank(message = "이름은 필수입니다")
    @Size(max = 20, message = "이름은 20자 이내")
    private String empName;

    @NotBlank(message = "이메일은 필수입니다")
    @Email(message = "이메일 형식이 아닙니다")
    private String email;

    @NotNull(message = "부서를 선택하세요")
    private Long deptId;

    @NotNull @PositiveOrZero(message = "급여는 0 이상")
    private Integer salary;

    @NotNull(message = "입사일은 필수입니다")
    @PastOrPresent(message = "입사일은 미래일 수 없습니다")
    private LocalDate hireDate;
}
```

자주 쓰는 것:

| 애노테이션 | 의미 |
|---|---|
| `@NotNull` / `@NotBlank` / `@NotEmpty` | null 아님 / 공백 아닌 문자열 / 빈 컬렉션 아님 |
| `@Size(min=, max=)` | 문자열·컬렉션 길이 |
| `@Min` / `@Max` / `@Positive` / `@PositiveOrZero` | 숫자 범위 |
| `@Email` / `@Pattern(regexp=)` | 형식 |
| `@Past` / `@Future` / `@PastOrPresent` | 날짜 |

## 2. 컨트롤러 — `@Valid` + `BindingResult`

```java
@PostMapping("/emps")
public String create(@Valid @ModelAttribute("form") EmpForm form,
                     BindingResult bindingResult,          // ★ @Valid 파라미터 바로 뒤
                     Model model, RedirectAttributes ra) {

    if (bindingResult.hasErrors()) {
        model.addAttribute("depts", deptService.findAll());
        return "emp/form";                                 // 폼으로 되돌아가 에러 표시
    }

    Long id = empService.register(form);
    ra.addFlashAttribute("message", "등록되었습니다");
    return "redirect:/emps/" + id;
}
```

- `BindingResult` 는 **반드시 `@Valid` 대상 파라미터 바로 다음**에 위치. 아니면 검증 실패 시
  `MethodArgumentNotValidException` 이 던져져 400.
- `@ModelAttribute("form")` 로 이름을 명시하면 뷰에서 `${form}` 으로 일관되게 접근.

## 3. Thymeleaf 에러 표시 (프로토타입 연결)

프로토타입 `emp-form.html` 의 `field--error` / `form-hint` 를 실제 검증에 연결합니다.

```html
<form th:object="${form}" method="post" th:action="@{/emps}">

  <div class="field" th:classappend="${#fields.hasErrors('empName')} ? 'field--error'">
    <label class="label" for="empName">이름 *</label>
    <input class="input" type="text" th:field="*{empName}">
    <p class="form-hint" th:if="${#fields.hasErrors('empName')}" th:errors="*{empName}">에러</p>
  </div>

  <div class="field" th:classappend="${#fields.hasErrors('email')} ? 'field--error'">
    <label class="label" for="email">이메일 *</label>
    <input class="input" type="email" th:field="*{email}">
    <p class="form-hint" th:errors="*{email}"></p>
  </div>

  <!-- 폼 전역 에러(필드 아님) -->
  <ul th:if="${#fields.hasGlobalErrors()}">
    <li th:each="e : ${#fields.globalErrors()}" th:text="${e}"></li>
  </ul>
</form>
```

- `#fields.hasErrors('empName')` : 그 필드에 에러가 있나.
- `th:errors="*{empName}"` : 그 필드의 에러 메시지(들)를 출력.
- `th:errorclass="field--error"` : 에러가 있으면 그 클래스를 자동 추가(위 `th:classappend` 축약).
- 에러가 있어 폼으로 되돌아와도, `th:field` 덕분에 **사용자가 입력했던 값은 그대로 유지**됩니다.

## 4. 커스텀 검증

### (A) 두 필드 관계 — 클래스 레벨 (`@ScriptAssert` 또는 커스텀)

```java
@Retention(RUNTIME) @Target(TYPE)
@Constraint(validatedBy = HireDateAfterBirthValidator.class)
public @interface HireDateAfterBirth {
    String message() default "입사일이 생년월일보다 빠릅니다";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}
```
```java
public class HireDateAfterBirthValidator implements ConstraintValidator<HireDateAfterBirth, EmpForm> {
    public boolean isValid(EmpForm f, ConstraintValidatorContext ctx) {
        if (f.getBirth() == null || f.getHireDate() == null) return true;   // null은 @NotNull이 담당
        return !f.getHireDate().isBefore(f.getBirth());
    }
}
```

### (B) DB를 봐야 하는 규칙 — 서비스/컨트롤러에서 `reject`

이메일 중복처럼 DB 조회가 필요한 건 애노테이션보다 **컨트롤러에서 직접**:

```java
if (empService.existsByEmail(form.getEmail())) {
    bindingResult.rejectValue("email", "duplicate", "이미 사용 중인 이메일입니다");
}
if (bindingResult.hasErrors()) { ... return "emp/form"; }
```

`rejectValue(필드, 코드, 기본메시지)` — `#fields.hasErrors('email')` 로 화면에 나옴.

## 5. 전역 예외 처리 — `@ControllerAdvice`

컨트롤러마다 try/catch 하지 않고 한곳에서.

```java
@Slf4j
@ControllerAdvice        // 화면(뷰) 반환용. REST는 @RestControllerAdvice
public class GlobalExceptionHandler {

    // 없는 리소스 → 404 화면
    @ExceptionHandler(NoSuchElementException.class)
    @ResponseStatus(HttpStatus.NOT_FOUND)
    public String notFound(NoSuchElementException e, Model model) {
        model.addAttribute("message", e.getMessage());
        return "error/404";
    }

    // 업무 규칙 위반 → 이전 화면 + 메시지 (예: 부서에 사원이 있어 삭제 불가)
    @ExceptionHandler(BusinessException.class)
    public String business(BusinessException e, RedirectAttributes ra) {
        ra.addFlashAttribute("error", e.getMessage());
        return "redirect:" + e.getReturnUrl();
    }

    // 그 외 전부 → 500 화면 + 로그
    @ExceptionHandler(Exception.class)
    @ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)
    public String etc(Exception e, Model model) {
        log.error("처리되지 않은 예외", e);
        model.addAttribute("message", "잠시 후 다시 시도해 주세요");
        return "error/500";
    }
}
```

- `@ExceptionHandler` 는 **가장 구체적인 타입**부터 매칭. 마지막에 `Exception.class` 로 catch-all.
- `@Order` 로 여러 advice 우선순위.
- `BusinessException` 같은 **커스텀 런타임 예외**를 만들어 서비스에서 던지면, 여기서 사용자 메시지로 변환.

### REST용

```java
@RestControllerAdvice
public class ApiExceptionHandler {

    @ExceptionHandler(MethodArgumentNotValidException.class)   // @Valid 실패 (JSON 요청)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public Map<String, Object> validation(MethodArgumentNotValidException e) {
        Map<String, String> errors = new LinkedHashMap<>();
        e.getBindingResult().getFieldErrors()
         .forEach(fe -> errors.put(fe.getField(), fe.getDefaultMessage()));
        return Map.of("code", "VALIDATION_ERROR", "errors", errors);
    }
}
```

## 6. 에러 페이지

`src/main/resources/templates/error/` 에 상태코드 이름으로 두면 부트가 자동 사용:

## 자주 하는 실수

- **`BindingResult` 위치가 `@Valid` 파라미터와 떨어짐** → 검증 실패 시 400. 반드시 바로 뒤.
- **`starter-validation` 미추가** → `@NotBlank` 등이 **무시**됨(붙였는데 검증이 안 됨).
- **에러인데 `depts` 를 다시 안 담고 `return "emp/form"`** → 부서 셀렉트가 비어 NPE. 필요한 모델을 다시 담는다.
- **에러 후 새 `EmpForm()` 을 만들어 넘김** → 사용자가 입력한 값이 날아감. 넘어온 `form` 그대로.
- **`@RestControllerAdvice` 인데 뷰 이름을 반환** → JSON으로 직렬화됨. 화면은 `@ControllerAdvice`.
- **모든 예외를 `Exception.class` 하나로만** → 404도 500으로 뭉개짐. 구체 타입부터.
- **서비스가 `NoSuchElementException` 던지는데 advice에 핸들러 없음** → Whitelabel 500.

## 핵심 요약

| 요소 | 내용 |
|---|---|
| Bean Validation | DTO 필드에 `@NotBlank` 등. `starter-validation` 필요 |
| `@Valid` + `BindingResult` | 컨트롤러에서 검증 결과 확인. 위치는 `@Valid` 바로 뒤 |
| Thymeleaf | `#fields.hasErrors('x')`, `th:errors="*{x}"`, `th:errorclass` |
| 커스텀 검증 | 두 필드 관계 → `ConstraintValidator` / DB 조회 → `bindingResult.rejectValue` |
| `@ControllerAdvice` | 전역 예외 처리(뷰). REST는 `@RestControllerAdvice` |
| `@ExceptionHandler` | 구체 타입부터. `Exception.class` 로 catch-all + 로그 |
| `templates/error/*.html` | 상태코드별 에러 페이지 |
