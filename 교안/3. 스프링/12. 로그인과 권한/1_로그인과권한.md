**Spring Security(부록 3·4)는 심화 과정으로 따로 빼뒀으므로**, 본 과정에서는 서블릿 표준

## 학습목표

- `HttpSession`이 무엇이고, 서버가 `JSESSIONID` 쿠키로 같은 사용자를 어떻게 알아보는지 설명한다.
- 로그인 폼 제출 → `MEMBER` 테이블 조회 → 성공 시 세션에 로그인 정보 저장을 구현한다.
- 로그아웃(`session.invalidate()`)을 구현한다.
- `HandlerInterceptor`로 "로그인 안 하면 `/login`으로 돌려보내기"를 페이지마다 반복하지 않고 한 곳에서 처리한다.
- **두 번째 인터셉터로 "ADMIN만 접근 가능한 경로"를 따로 통제**할 수 있다.
- Thymeleaf 화면에 "OO님 환영합니다"처럼 로그인한 사용자 정보를 표시한다.
- 이 방식의 남은 한계(CSRF 방어 없음, URL 단위라 서비스 계층까지는 못 막음)를 알고, Spring Security(부록)로 가야 할 때를 안다.

## 1. `HttpSession`이란

HTTP는 원래 요청-응답이 끝나면 아무것도 기억하지 못하는(stateless) 프로토콜입니다. 그런데
로그인을 하면 다음 페이지로 이동해도 "로그인한 상태"가 유지됩니다 — 서버가 **세션**이라는
저장 공간을 만들고, 브라우저에는 그 세션을 찾아올 열쇠인 `JSESSIONID` 쿠키를 심어주기 때문입니다.

```
① 로그인 성공 → 서버가 세션 생성(메모리에 Map처럼 저장) + JSESSIONID 쿠키를 응답에 실어 보냄
② 브라우저는 이후 모든 요청에 JSESSIONID 쿠키를 자동으로 실어 보냄
③ 서버는 그 쿠키로 "몇 번 세션인지" 찾아서 로그인 정보를 꺼냄
```

스프링 부트(내장 톰캣)가 이 쿠키 발급·세션 관리를 전부 대신 해줍니다. 우리는
`HttpServletRequest`에서 `request.getSession()`으로 세션 객체만 얻어 쓰면 됩니다.

```java
HttpSession session = request.getSession();   // 없으면 새로 생성, 있으면 기존 것
session.setAttribute("loginMember", member);  // 저장
Member m = (Member) session.getAttribute("loginMember");  // 꺼내기
session.invalidate();                          // 세션 통째로 폐기 (로그아웃)
```

## 2. `MEMBER` 테이블 — 로그인 + 역할(ROLE)

```sql
CREATE TABLE MEMBER (
    MEMBER_ID   VARCHAR(20) PRIMARY KEY,
    PASSWORD    VARCHAR(100) NOT NULL,          -- 해시 저장 (아래 3절)
    MEMBER_NAME VARCHAR(20)  NOT NULL,
    ROLE        VARCHAR(10)  NOT NULL DEFAULT 'USER'   -- 'ADMIN' 또는 'USER'
);
```

권한이 여러 개 겹칠 수 있는 시스템이라면 `MEMBER_ROLE`을 별도 테이블(다대다)로 분리하지만,
"관리자냐 아니냐" 둘 중 하나만 구분하면 되는 지금은 `MEMBER`에 컬럼 하나로 충분합니다
(여러 역할이 필요해지면 부록 3에서 `MEMBER_ROLE` 테이블로 확장).

```java
package com.example.hr.domain;

import lombok.*;

@Getter @Builder @AllArgsConstructor @NoArgsConstructor
public class Member {
    private String memberId;
    private String password;
    private String memberName;
    private String role;   // "ADMIN" / "USER"
}
```

```java
@Mapper
public interface MemberMapper {
    Member findById(String memberId);
}
```

```xml
<select id="findById" resultType="Member">
  SELECT MEMBER_ID, PASSWORD, MEMBER_NAME, ROLE FROM MEMBER WHERE MEMBER_ID = #{memberId}
</select>
```

## 3. 비밀번호는 평문 저장 금지 — `BCrypt`

Spring Security 전체를 붙이지 않아도, 해시 함수만 필요하면 `spring-security-crypto` 모듈
하나만 가볍게 추가해 쓸 수 있습니다(필터 체인·`SecurityConfig` 등은 전혀 안 딸려 옵니다).

```groovy
implementation 'org.springframework.security:spring-security-crypto'
```

```java
BCryptPasswordEncoder encoder = new BCryptPasswordEncoder();
String hashed = encoder.encode("1234");           // 회원가입 시 저장할 값
boolean ok = encoder.matches("1234", hashed);      // 로그인 시 검증
```

`encoder.matches(입력값, 저장된해시)` 는 매번 다르게 생긴 해시라도 같은 원문이면 `true` 를
반환합니다(BCrypt는 매번 랜덤 salt를 섞어 해시하기 때문에 `hashed` 값 자체는 매번 다릅니다).

## 4. 로그인/로그아웃 컨트롤러

```java
@Controller
@RequiredArgsConstructor
public class LoginController {

    private final MemberMapper memberMapper;
    private final BCryptPasswordEncoder encoder = new BCryptPasswordEncoder();

    @GetMapping("/login")
    public String loginForm() {
        return "login";
    }

    @PostMapping("/login")
    public String login(@RequestParam String memberId, @RequestParam String password,
                         HttpServletRequest request, Model model) {
        Member member = memberMapper.findById(memberId);
        if (member == null || !encoder.matches(password, member.getPassword())) {
            model.addAttribute("error", "아이디 또는 비밀번호가 올바르지 않습니다.");
            return "login";
        }
        request.getSession().setAttribute("loginMember", member);
        return "redirect:/";
    }

    @PostMapping("/logout")
    public String logout(HttpServletRequest request) {
        request.getSession().invalidate();
        return "redirect:/login";
    }
}
```

로그인 실패를 리다이렉트가 아니라 **같은 뷰를 다시 그리며 에러 메시지를 담아 반환**하는 이유:
`redirect:`를 쓰면 입력값·에러가 다음 요청으로 안 넘어가 화면에 못 띄웁니다(Day 10 3절 참고).

## 5. `HandlerInterceptor` — 페이지마다 로그인 체크 반복하지 않기

컨트롤러 메서드마다 "로그인 안 했으면 돌려보내기"를 매번 쓰면 실수로 하나 빠뜨리기 쉽습니다.
**인터셉터**가 컨트롤러 호출 전에 공통으로 검사하게 만듭니다.

```java
public class LoginCheckInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        HttpSession session = request.getSession(false);   // 없으면 새로 만들지 않음
        if (session == null || session.getAttribute("loginMember") == null) {
            response.sendRedirect("/login");
            return false;   // false = 컨트롤러 호출 안 하고 여기서 끝
        }
        return true;
    }
}
```

`excludePathPatterns`에 로그인 페이지 자신과 정적 리소스를 빼두지 않으면, 로그인 페이지로
가려다 다시 로그인 페이지로 튕기는 무한 리다이렉트에 빠집니다 — 실습에서 자주 걸리는 함정.

## 6. 두 번째 인터셉터로 권한(인가) 나누기 — ADMIN만

로그인 여부는 "전 구간 공통"이지만, "ADMIN만"은 **일부 경로에만** 적용됩니다. 인터셉터를
하나 더 만들어 **좁은 경로에만** 등록하면 됩니다.

```java
public class AdminOnlyInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler)
            throws IOException {
        HttpSession session = request.getSession(false);
        Member member = session != null ? (Member) session.getAttribute("loginMember") : null;

        if (member == null || !"ADMIN".equals(member.getRole())) {
            response.sendError(HttpServletResponse.SC_FORBIDDEN, "관리자만 접근할 수 있습니다.");
            return false;
        }
        return true;
    }
}
```

```java
@Configuration
public class WebConfig implements WebMvcConfigurer {

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new LoginCheckInterceptor())
                .excludePathPatterns("/login", "/logout", "/css/**", "/js/**", "/images/**");

        registry.addInterceptor(new AdminOnlyInterceptor())
                .addPathPatterns("/depts/**", "/emps/*/delete");
    }
}
```

두 인터셉터는 **등록한 순서대로** 실행됩니다. `/depts/**`로 요청이 오면 ①
`LoginCheckInterceptor`가 먼저 "로그인은 했는지"를 보고, 통과하면 ② `AdminOnlyInterceptor`가
"ADMIN인지"를 봅니다 — 로그인 여부와 권한 여부를 **각각 다른 인터셉터의 책임**으로 나눈 것입니다.

**한계**: 이건 **URL 경로 단위**로만 막습니다. 만약 `DeptService.delete()` 를 다른 컨트롤러나
배치 코드에서 URL을 거치지 않고 직접 호출하면 이 검사를 그냥 통과합니다. 정말 안전하게
하려면 서비스 메서드 자체에서도 한 번 더 확인하거나(권한 정보를 파라미터로 넘기기), 부록
3~4에서 배우는 **메서드 보안**(`@PreAuthorize("hasRole('ADMIN')")`)처럼 메서드에 선언만 하면
어떤 경로로 호출되든 걸러주는 방식으로 가야 합니다.

## 7. 화면에 로그인 사용자 표시

컨트롤러마다 `model.addAttribute("loginMember", ...)` 를 반복하지 않도록, 공통 처리는
`@ControllerAdvice` + `@ModelAttribute` 로 모읍니다.

```java
@ControllerAdvice
public class GlobalModelAdvice {

    @ModelAttribute("loginMember")
    public Member loginMember(HttpServletRequest request) {
        HttpSession session = request.getSession(false);
        return session != null ? (Member) session.getAttribute("loginMember") : null;
    }
}
```

```html
<div th:if="${loginMember != null}">
  <span th:text="${loginMember.memberName} + '님 환영합니다'"></span>
  <a th:if="${loginMember.role == 'ADMIN'}" th:href="@{/depts}">부서 관리</a>
  <form th:action="@{/logout}" method="post"><button type="submit">로그아웃</button></form>
</div>
```

메뉴에서 링크를 숨기는 건 **화면 편의**일 뿐, 진짜 방어는 6절의 인터셉터입니다. 링크를 숨겨도
주소를 직접 입력하면 접근할 수 있으므로, 화면 숨김과 서버 검사는 항상 같이 갑니다.

## 자주 하는 실수

- **`request.getSession()` vs `request.getSession(false)`** — 인자 없이 호출하면 세션이
  없을 때 **새로 만듭니다**. 로그인 여부만 확인할 땐 `getSession(false)`로 "있으면 가져오고
  없으면 null"을 받아야, 없는 세션을 검사할 때마다 새로 만드는 낭비가 없습니다.
- **`excludePathPatterns`에 로그인 경로를 빼먹음** → 무한 리다이렉트.
- **비밀번호를 평문 비교(`equals`)** → 반드시 `BCryptPasswordEncoder.matches()`.
- **정적 리소스(`/css/**`, `/js/**`)를 인터셉터에서 안 뺌** → 로그인 안 한 사용자에게 CSS가
  하나도 안 먹은 깨진 화면이 나감.
- **로그아웃을 GET으로 구현** → 링크를 클릭하기만 해도(또는 크롤러가 따라가도) 로그아웃되는
  부작용. `POST`로 폼 제출해야 안전.
- **화면에서 메뉴만 숨기고 서버 검사(6절)를 빼먹음** → 주소창에 직접 URL을 쳐서 우회 가능.
- **`AdminOnlyInterceptor`를 `LoginCheckInterceptor`보다 먼저 등록** → 비로그인 사용자가
  `AdminOnlyInterceptor`에서 `NullPointerException` 없이 걸러지긴 하지만(방어 코드가 있어서),
  로그인 페이지로 안내받지 못하고 403만 받는 등 사용자 경험이 나빠질 수 있음. 항상 "로그인 → 권한" 순서.

## 핵심 요약

| 요소 | 내용 |
|---|---|
| `HttpSession` | 서버가 `JSESSIONID` 쿠키로 사용자를 식별해 로그인 상태를 유지 |
| `session.setAttribute`/`getAttribute`/`invalidate` | 저장 / 조회 / 로그아웃 |
| `spring-security-crypto` | Security 프레임워크 전체 없이 `BCryptPasswordEncoder`만 가볍게 사용 |
| `HandlerInterceptor.preHandle` | 컨트롤러 호출 전 공통 검사, `false` 반환 시 요청 중단 |
| `LoginCheckInterceptor` | 전 구간, 로그인 여부(인증) |
| `AdminOnlyInterceptor` | 좁은 경로만, 역할 확인(인가) |
| `WebMvcConfigurer.addInterceptors` | 인터셉터 등록 순서 + 경로 범위(`addPathPatterns`/`excludePathPatterns`) |
| `@ControllerAdvice` + `@ModelAttribute` | 모든 뷰에 공통으로 넘길 값(로그인 사용자) 처리 |

## 이 방식의 남은 한계 — 부록으로 가야 할 때

인증(로그인)과 기본 인가(ADMIN 여부)는 오늘 다 만들었습니다. 다음이 필요해지면 **부록
3(Spring Security 기초)·4(인증 심화)** 로:

- **URL이 아니라 메서드 단위로 방어**(`@PreAuthorize`) — 호출 경로가 여러 개여도 안전
- **CSRF 방어** — 지금 이 로그인/삭제 폼은 CSRF 토큰이 없어 위조 요청에 취약
- **비밀번호 정책·계정 잠금·동시 세션 제한** 같은 인증 부가 기능
- 역할이 여러 개로 늘어나면 `MEMBER_ROLE`(다대다)로 확장
- REST API를 만든다면(Day 16) 토큰 기반 인증(**부록 2. JWT**)도 대안
