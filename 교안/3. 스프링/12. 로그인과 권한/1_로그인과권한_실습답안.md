## 문제 2. 실패 메시지를 뭉뚱그리는 이유

아이디는 맞는데 비밀번호만 틀렸다고 알려주면, 공격자가 그 응답 차이만으로 **어떤 아이디가
실제로 존재하는지**를 하나씩 확인(계정 열거, account enumeration)할 수 있습니다. 존재 여부와
비밀번호 오류를 구분하지 않고 항상 같은 메시지("아이디 또는 비밀번호가 올바르지 않습니다")로
합쳐야 이 정보 노출을 막습니다.

## 문제 3. 인터셉터 재현

`excludePathPatterns`에서 `/login`을 빼먹으면: 비로그인 상태로 `/emps` 접속 → `/login`으로
리다이렉트 → 그런데 `/login` 자체도 인터셉터에 걸림 → 다시 `/login`으로 리다이렉트 → **무한
리다이렉트**(브라우저가 "리다이렉트가 너무 많습니다" 오류를 띄움). `/css/**`를 빼먹으면
리다이렉트 자체는 안 나지만, 로그인 페이지가 CSS 없이 깨진 채로 보입니다(스타일시트 요청도
인터셉터에 걸려 `/login`으로 우회되어 CSS가 아닌 HTML이 응답으로 옴).

## 문제 5. 세션과 쿠키

`JSESSIONID` 쿠키는 세션을 찾아오는 **열쇠**일 뿐, 세션 데이터 자체는 서버 메모리에 있습니다.
`session.invalidate()`는 서버 쪽 세션(열쇠로 찾아갈 방)을 통째로 없애버립니다. 브라우저에
쿠키 값이 그대로 남아있어도, 그 값으로 찾아갈 세션이 서버에 더 이상 없으므로 다음 요청부터는
"로그인 안 된 상태"로 취급됩니다(서버가 새 세션을 만들거나 `getSession(false)`가 `null`을 반환).

## 문제 6. `AdminOnlyInterceptor`

`user`로 로그인 후 `/depts` 접속 → `AdminOnlyInterceptor.preHandle`이 `role`이 `ADMIN`이
아님을 확인하고 403 응답. `admin`으로는 정상 통과. 등록 순서를 바꿔 `AdminOnlyInterceptor`를
먼저 등록해도, **두 인터셉터 모두 `/depts/**` 요청엔 여전히 순서대로 다 실행**되므로 결과
자체(로그인 안 했으면 결국 막힘)는 같습니다. 다만 비로그인 상태로 `/depts`에 접속했을 때,
`LoginCheckInterceptor`가 먼저면 "로그인 페이지로 리다이렉트"를 받고, `AdminOnlyInterceptor`가
먼저면 세션이 아예 없어 `member == null`로 걸려 "403 관리자만 접근"을 먼저 받습니다 — 로그인도
안 한 사용자에게 "권한이 없다"는 메시지가 먼저 뜨는 건 사용자 경험상 부적절하므로, **인증
검사(로그인)를 인가 검사(권한)보다 먼저 등록**해야 합니다.
