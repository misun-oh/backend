# Day 12. 로그인과 권한 — 심화 (경험자용)

## 1. `HandlerInterceptor` vs 서블릿 `Filter`

- **Filter**: 서블릿 컨테이너 레벨. `DispatcherServlet`보다 **먼저** 실행되고, 스프링 빈이
  아니어도 동작(단, `@Component`로 등록하면 스프링이 관리). 정적 리소스까지 포함해 모든 요청을 가로챈다.
- **Interceptor**: 스프링 MVC 레벨. `DispatcherServlet`이 컨트롤러를 찾은 **후**, 실제 호출
  직전(`preHandle`)/응답 직전(`postHandle`)/완료 후(`afterCompletion`)에 끼어든다. `HandlerMethod`
  (어떤 컨트롤러·메서드가 호출될지) 정보에 접근할 수 있어 어노테이션 기반 처리(`@LoginRequired` 커스텀
  애노테이션 등)에 유리.
- 로그인 체크처럼 "스프링 MVC 흐름 안에서, 컨트롤러가 뭔지 알고 판단"하는 경우는 Interceptor가 자연스럽다.
  Spring Security의 필터 체인은 이보다 훨씬 앞단(Filter 레벨)에서 동작 — 그래서 인증/인가를
  MVC보다 더 근본적으로 통제할 수 있다(부록 3에서 이 위치 차이를 다시 다룸).

## 2. 세션 고정 공격(Session Fixation)과 로그인 시 세션 재발급

공격자가 미리 알아낸 `JSESSIONID`를 피해자에게 심어두고, 피해자가 그 세션으로 로그인하면
공격자도 같은 세션(=로그인 상태)을 쓸 수 있게 되는 공격입니다. 대응: **로그인에 성공하는
순간 기존 세션을 버리고 새 세션을 발급**합니다.

```java
request.changeSessionId();   // 서블릿 3.1+ 표준: 세션은 유지하되 ID만 재발급
```

또는 `request.getSession().invalidate()` 후 `request.getSession(true)`로 완전히 새 세션을
만들고 그 위에 `loginMember`를 다시 채우는 방법도 있습니다. Spring Security를 쓰면 이 처리가
기본 정책(`sessionFixation().migrateSession()`)으로 자동 적용됩니다.

## 3. 쿠키 보안 옵션

```yaml
server:
  servlet:
    session:
      cookie:
        http-only: true    # 기본값. JS(document.cookie)로 쿠키를 못 읽게 해서 XSS로 인한 세션 탈취 방지
        secure: true        # HTTPS에서만 쿠키 전송 (운영 환경)
        same-site: lax       # 다른 사이트에서 오는 요청엔 쿠키를 안 실음 (CSRF 완화)
      timeout: 30m
```

## 4. 서버가 여러 대라면 — 세션 공유 문제

지금처럼 세션이 **애플리케이션 서버 메모리**에 있으면, 서버를 2대 이상 띄우고 로드밸런서를
앞에 두는 순간 "1번 서버에 로그인했는데 2번 서버로 요청이 가면 로그인이 안 풀려 있는" 문제가
생깁니다. 실무 해법:

- **Sticky session**: 로드밸런서가 같은 사용자를 항상 같은 서버로 보냄 (임시방편)
- **세션 클러스터링/외부 저장소**: Redis 등에 세션을 저장하고 모든 서버가 공유(`Spring
  Session` + `spring-session-data-redis`)
- **아예 서버가 상태를 안 가짐(stateless)**: 부록 2. JWT — 토큰에 정보를 담아 보내므로
  어느 서버가 받아도 검증만 하면 됨. 세션 공유 문제 자체가 없어짐

## 5. `@ModelAttribute`의 실행 시점 주의

`@ControllerAdvice` 의 `@ModelAttribute` 메서드는 **같은 클래스의 모든 `@RequestMapping`
메서드 호출 전에 매번 실행**됩니다. 여기서 DB 조회를 하면(예: 매번 `MemberMapper`로 다시
조회) 불필요한 쿼리가 늘어나므로, 이 챕터처럼 **세션에 이미 있는 값을 꺼내기만** 하는 용도로
쓰는 것이 적절합니다. 최신 정보(변경된 이름 등)가 꼭 필요하면 로그인/정보수정 시점에 세션
값도 같이 갱신해 둡니다.
