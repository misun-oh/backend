Day 4

IoC와 DI

제어의 역전(IoC)과 의존성 주입(DI) — 그림으로 한 번에 보기

한 줄 요약 — "누가 객체를 만들고 연결하는가"의 주인이 내 코드에서 스프링 컨테이너로 바뀌는 것, 그게 IoC입니다. DI는 그 결과로 "필요한 걸 컨테이너가 넣어주는" 방식입니다.

3 생성자 주입 vs 필드 주입

✓ 생성자 주입 (기본)

  • final 가능 — 불변, 주입 누락은 컴파일에서 발견
  • 의존성이 생성자 시그니처에 다 드러남
  • new EmpService(mockMapper) — 스프링 없이 테스트 가능
  • 순환 참조를 기동 시 즉시 발견

✗ 필드 주입 (지양)

  • @Autowired private ... — final 불가
  • 클래스를 다 읽어야 의존성을 알 수 있음
  • 리플렉션 없이는 값을 못 채움 → 테스트 불편
  • 순환 참조가 런타임에 늦게 터짐

4 빈의 생애 — 스코프와 생명주기

sequenceDiagram
  participant C as ApplicationContext
  participant B as 빈 (예: CacheWarmer)
  C->>B: 1. 생성자 호출 (의존성 주입)
  C->>B: 2. @PostConstruct 메서드 실행
  Note over B: 이후 앱 실행 내내 대기·사용됨 (singleton)
  C->>B: 3. 컨테이너 종료 직전 @PreDestroy 실행
singleton (기본) prototype (조회마다 새로) request / session (웹 스코프)

핵심만 다시

  • IoC = 객체 생성·연결·소멸의 제어권이 컨테이너에 있다.
  • DI = 필요한 협력 객체를 컨테이너가 생성자로 넣어준다.
  • 빈 등록은 ①스캔 ②@Bean ③@Configuration 세 가지뿐.
  • 주입은 생성자 주입이 기본, 필드 주입은 지양.
  • 같은 타입이 여럿이면 @Primary(기본 하나) 또는 @Qualifier(이름 지정).
  • 싱글턴 빈에는 상태(가변 필드)를 두지 않는다 — 동시성 버그의 원인.
