# Day 1. 사원관리 시스템 설계 — 실습

교안에서 **사원(Emp)** 기능을 설계했습니다. 이번 실습에서는 같은 방법으로 **부서(Dept)**
기능을 직접 설계합니다. 도구는 Mermaid를 씁니다 (마크다운에 ```` ```mermaid ```` 블록).

## 부서 기능 요구사항

| # | 요구사항 |
|---|---|
| D1 | 인사담당자는 전체 부서를 목록으로 보고 싶다. 목록에는 부서명·근무지·**소속 인원수**·**평균 급여**가 나온다. |
| D2 | 새 부서를 추가하고, 기존 부서명·근무지를 수정하고 싶다. |
| D3 | 부서를 삭제하고 싶다. 단, 소속 사원이 있는 부서는 함부로 지우면 안 된다. |
| D4 | 부서 관리는 로그인한 인사담당자만 할 수 있다. |

프로토타입: `prototypes/templates/hr/depts.html` (부서 목록 + "부서 추가" 모달).

## 문제 5. 개념 — 도메인에 얹을까, 전용 DTO로 뺄까

사원 **목록 화면**에는 각 사원의 **부서명**이 보여야 합니다. `EMP` 테이블에는 `DEPT_ID`만 있습니다.
다음 세 가지 중 무엇이 옳은 설계인지 고르고, 나머지 둘이 왜 문제인지 각각 한 줄로 쓰세요.

- (A) 목록 조회 SQL에서 `EMP JOIN DEPT` 하고, 부서명을 `Emp`의 **읽기 전용 필드** `deptName`에 담는다.
- (B) 화면(Thymeleaf)에서 사원마다 부서를 한 번씩 다시 조회한다.
- (C) `Emp`에 `deptName` + `부서별 평균급여` + `행 선택여부`를 모두 필드로 추가한다.

**추가로 답하기**: 부서 목록 화면은 부서마다 `소속 인원수`·`평균 급여`가 필요합니다(문제 3의 `DeptListRow`).
이건 왜 `Dept` 도메인에 필드로 얹지 않고 전용 DTO로 뺐는지, (A)의 `deptName`과 무엇이 다른지 한 줄로 쓰세요.

## 문제 6. 정책 결정 — 부서 삭제 (심화)

D3 "소속 사원이 있는 부서는 함부로 지우면 안 된다"를 어떻게 구현할지 **정책을 하나 정하고**,
문제 4의 시퀀스 다이어그램에 그 분기를 추가하세요.

**힌트**: 흔한 정책 3가지 — ① 소속 사원이 있으면 삭제를 막고 에러 메시지, ② 소속 사원을
"미배정"으로 옮긴 뒤 삭제, ③ 실제로 지우지 않고 `사용여부='N'`으로 표시(soft delete).
