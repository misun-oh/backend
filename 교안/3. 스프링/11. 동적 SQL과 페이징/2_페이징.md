## 학습목표

- `cond`에 `page`/`size`를 추가해 `LIMIT ? OFFSET ?` 계산에 사용할 수 있다.
- 별도 `COUNT(*)` 로 검색조건이 반영된 전체 건수를 구할 수 있다.
- hr 프로젝트에 이미 있는 `PageDto`(페이지 블럭 방식)에 전체 건수를 넘겨 페이지 네비게이션을 만들 수 있다.
- 정렬 컬럼을 `${}` 로 넣되 **화이트리스트(enum)** 로만 허용한다.
- 페이지 링크에 검색 조건을 유지하며 화면을 완성한다.

---

## 1. `cond` 확장 — `page`, `size`, `offset`

`1_동적SQL과검색.md`에서 만든 `EmpSearchCond`에 페이지 요청 정보를 추가합니다.

```java
// dto/EmpSearchCond.java
@Data
public class EmpSearchCond {
    private String keyword;
    private String deptId;
    private boolean workingOnly;
    private EmpSort sort = EmpSort.EMP_ID;   // 4절에서 만든다

    private int page = 1;   // 1부터 시작
    private int size = 10;  // 페이지당 게시물 수

    // LIMIT #{size} OFFSET #{offset} 에서 사용
    public int getOffset() {
        return (Math.max(page, 1) - 1) * size;
    }
}
```

> `getOffset()` 처럼 **필드가 없어도 getter만 있으면** MyBatis가 `#{offset}` 으로 바인딩할 수
> 있습니다. OGNL·SpringEL 모두 "프로퍼티"를 getter 기준으로 찾기 때문입니다.

---

## 2. `LIMIT` + `COUNT` — 왜 두 개의 SQL이 필요한가

지금까지는 `selectByCond` 가 조건에 맞는 **전체 결과**를 돌려줬기 때문에, 리스트의 크기(`size()`)가
곧 전체 건수였습니다. 그런데 `LIMIT` 을 붙이면 한 페이지 분량만 돌아오므로, **전체 건수를 따로
구하는 SQL이 하나 더 필요**합니다. 이때 두 SQL이 **같은 WHERE 조건**을 써야 페이지 수가 맞으므로,
검색 문서에서 만든 `<sql id="searchWhere">` 를 그대로 재사용합니다.

```xml
<!-- searchWhere 는 1_동적SQL과검색.md 5절에서 이미 정의되어 있음 -->

<select id="selectByCond" resultType="EmpDto">
  SELECT e.emp_id, e.emp_name, e.email, e.emp_no,
         e.dept_id, d.dept_title AS deptName,
         e.hire_date, e.ent_yn, e.phone, e.salary, e.bonus
  FROM emp e
  LEFT JOIN dept d ON e.dept_id = d.dept_id
  <include refid="searchWhere"/>
  ORDER BY ${sort.column} ${sort.direction}
  LIMIT #{size} OFFSET #{offset}
</select>

<select id="countByCond" resultType="int">
  SELECT COUNT(*)
  FROM emp e
  <include refid="searchWhere"/>
</select>
```

```java
// EmpMapper.java
List<EmpDto> selectByCond(EmpSearchCond cond); // ORDER BY + LIMIT/OFFSET 추가됨
int countByCond(EmpSearchCond cond);           // 신규
```

> `COUNT(*)` 는 조인을 안 해도 되면 빼서 더 빠르게(여기선 DEPT 조인이 결과 수에 영향 없으므로
> `FROM emp e` 만으로도 됨). 대량이면 커버링 인덱스·키셋 페이징(심화 문서 참고).

## 3. `PageDto` 로 페이지 네비게이션 만들기

새 클래스를 만들 필요 없이, hr 프로젝트에 **이미 있는** `PageDto`(생성자 `(page, totalCnt)`)를
그대로 씁니다. 페이지 블럭(`sPageNo`~`ePageNo`), 이전/다음(`isPrev`/`isNext`)까지 전부 계산해줍니다.

```java
@Override
public void selectByCond(EmpSearchCond cond, Model model) {
    // countByCond·selectByCond는 서로 독립적인 쿼리 - 둘 다 실행한 뒤에 PageDto를 만든다
    int totalCnt = mapper.countByCond(cond);
    List<EmpDto> list = mapper.selectByCond(cond);

    model.addAttribute("list", list);
    model.addAttribute("totalCnt", totalCnt);
    model.addAttribute("pageDto", new PageDto(cond.getPage(), totalCnt));
}
```

> **주의**: `PageDto` 생성자에 넘기는 `totalCnt` 는 반드시 `countByCond(cond)` 로 구한, **검색조건이
> 반영된** 건수여야 합니다. 조건 없는 전체 건수를 넘기면 페이지 수가 실제 검색 결과와 안 맞습니다.

> **`cond.size`를 바꿔도 되나?** `PageDto` 내부의 페이지당 건수는 `private int size = 10;` 으로
> **고정**되어 있고, 생성자로 바꿀 방법이 없습니다. 반면 `cond.size`는 자유롭게 바꿀 수 있는
> 필드입니다. 실제 조회(`LIMIT #{size}`)는 `cond.getSize()`를 따르지만, `PageDto`의 페이지 블럭
> 계산(`sPageNo`~`ePageNo`, `isNext`)은 여전히 내부 고정값 10을 기준으로 계산되므로, `cond.size`를
> 10이 아닌 값으로 바꾸면 **화면의 페이지 번호와 실제 데이터가 어긋납니다.** 이 챕터에서는 항상
> 10으로만 쓰고, "페이지당 20개씩 보기" 같은 기능이 필요해지면 `PageDto`도 함께 손봐야 합니다
> (`2_페이징_심화.md` 참고).

## 4. 정렬 — `${}` 는 enum으로만

`ORDER BY ${...}` 는 값이 아니라 SQL 조각이라 `#{}` 를 못 씁니다. 그래서 **임의 문자열이 못 들어오게**
enum으로 제한합니다.

```java
// dto/EmpSort.java
public enum EmpSort {
    EMP_ID("emp_id", "asc"),
    HIRE_DATE("hire_date", "desc"),
    SALARY("salary", "desc"),
    NAME("emp_name", "asc");

    private final String column;
    private final String direction;

    EmpSort(String column, String direction) {
        this.column = column;
        this.direction = direction;
    }

    public String getColumn() { return column; }
    public String getDirection() { return direction; }
}
```

컨트롤러가 `?sort=SALARY` 를 받으면 스프링이 문자열을 `EmpSort.valueOf("SALARY")` 로 자동 변환한다
(`@ModelAttribute EmpSearchCond cond` 의 `sort` 필드). 목록에 없는 값이면 400. XML에서는
`${sort.column} ${sort.direction}` → `salary desc`. 사용자가 `sort` 문자열을 조작해도 enum 상수
밖은 못 만듭니다.

## 5. 화면 연결 — 페이지네이션 붙이기

검색폼(`1_동적SQL과검색.md` 6절)에 정렬 select를 추가하고, 그 아래에 페이지네이션을 붙입니다.

```html
<!-- 검색폼에 정렬 select 추가 -->
<select class="select" th:field="*{sort}">
  <option value="HIRE_DATE">입사일순</option>
  <option value="NAME">이름순</option>
  <option value="SALARY">급여순</option>
  <option value="EMP_ID">사번순</option>
</select>
```

```html
<!-- 페이지네이션: PageDto 의 페이지 블럭(sPageNo~ePageNo) + cond 로 조건 유지 -->
<nav class="pagination" th:if="${pageDto.ePageNo >= pageDto.sPageNo}">
  <a th:if="${pageDto.prev}"
     th:href="@{/emps(keyword=${cond.keyword}, deptId=${cond.deptId}, workingOnly=${cond.workingOnly}, sort=${cond.sort}, page=${pageDto.sPageNo - 1})}">‹</a>
  <a th:each="p : ${#numbers.sequence(pageDto.sPageNo, pageDto.ePageNo)}"
     th:href="@{/emps(keyword=${cond.keyword}, deptId=${cond.deptId}, workingOnly=${cond.workingOnly}, sort=${cond.sort}, page=${p})}"
     th:text="${p}"
     th:classappend="${p == pageDto.page} ? 'is-current' : ''"></a>
  <a th:if="${pageDto.next}"
     th:href="@{/emps(keyword=${cond.keyword}, deptId=${cond.deptId}, workingOnly=${cond.workingOnly}, sort=${cond.sort}, page=${pageDto.ePageNo + 1})}">›</a>
</nav>
```

> `${pageDto.prev}` / `${pageDto.next}` 는 각각 `isPrev()`/`isNext()` 게터를 호출한다(스프링EL이
> boolean 프로퍼티를 `isXxx()` 로 찾는 규칙). 페이지 링크에 **현재 검색 조건(`cond`)을 계속
> 붙여야** 2페이지로 넘어가도 검색이 유지된다.

---

## 자주 하는 실수

- **정렬을 `#{sort}` 로** → `ORDER BY '?'` 가 되어 정렬 안 됨(문자열 상수로 정렬). `${}` + enum.
- **`${}` 에 사용자 문자열 그대로** → 인젝션. enum·화이트리스트 필수.
- **COUNT SQL의 WHERE 를 데이터 SQL과 다르게** → 페이지 수가 안 맞음. `<sql>` 로 공유.
- **페이지 링크에 검색 조건 안 붙임** → 2페이지에서 검색이 풀림.
- **`PageDto` 생성자에 조건 반영 전 전체 건수를 넘김** → 반드시 `countByCond(cond)` 결과를 넘겨야 한다.
- **`cond.size`를 10이 아닌 값으로 바꿈** → `PageDto`는 여전히 내부 고정값 10 기준으로 페이지를 계산하므로 네비게이션이 실제 데이터와 어긋난다. `PageDto`도 함께 고쳐야 한다.
