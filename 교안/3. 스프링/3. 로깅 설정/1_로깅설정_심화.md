# Day 3. 로깅 설정 — 심화 (경험자용)

## 1. MDC — 요청 하나를 로그에서 추적하기

동시에 여러 요청이 처리되면 로그가 뒤섞입니다. **MDC**(Mapped Diagnostic Context)에 요청별 키를 넣어
두면 그 요청의 모든 로그에 자동으로 따라붙습니다.

```java
@Component
public class RequestIdFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        MDC.put("reqId", UUID.randomUUID().toString().substring(0, 8));
        try {
            chain.doFilter(req, res);
        } finally {
            MDC.clear();   // 스레드 재사용되므로 반드시 정리
        }
    }
}
```

```
pattern: "%d %-5level [%X{reqId}] %logger - %msg%n"
```
→ `14:02:11 INFO  [a1b2c3d4] c.e.h.EmpService - 사원 등록 시작` 처럼 같은 `reqId` 로 묶여 보입니다.
Spring Cloud Sleuth/Micrometer Tracing 을 쓰면 traceId/spanId 를 자동으로 MDC에 넣어 줍니다.

## 2. 구조화 로깅(JSON) — 로그 수집 시스템용

운영에서 ELK/Loki/CloudWatch 로 로그를 모으려면 텍스트보다 **JSON 한 줄**이 파싱하기 좋습니다.

- Spring Boot 3.4 이후(4.0 포함) : `logging.structured.format.console=ecs`(또는 `logstash`, `gelf`) 로 내장 지원.
- 그 이전 : `net.logstash.logback:logstash-logback-encoder` 의 `LogstashEncoder`.

```json
{"@timestamp":"2026-08-28T14:02:11.123Z","level":"INFO","logger":"c.e.h.EmpService",
 "message":"사원 등록 완료","reqId":"a1b2c3d4","empId":221}
```

`log.atInfo().addKeyValue("empId", 221).log("사원 등록 완료")` (SLF4J 2.0 fluent API)로 필드를 넣습니다.

## 3. 성능: 파라미터 평가 지연

`{}` 바인딩도 인자 자체는 평가됩니다. `log.debug("dump={}", expensive())` 는 `expensive()` 가
항상 실행됩니다. 정말 비싼 경우:

```java
if (log.isDebugEnabled()) {
    log.debug("dump={}", expensive());
}
// 또는 SLF4J 2.0 fluent + Supplier
log.atDebug().addArgument(() -> expensive()).log("dump={}");
```

## 4. 로거 레벨을 런타임에 바꾸기

재배포 없이 특정 패키지 로그를 잠깐 올리고 싶을 때 — Actuator `loggers` 엔드포인트:

```
GET  /actuator/loggers/com.example.hr        → 현재 레벨
POST /actuator/loggers/com.example.hr        { "configuredLevel": "DEBUG" }
```

운영에서는 이 엔드포인트를 Security로 보호하고, 조사 끝나면 원복(`null` 로 POST).

## 5. `logback-spring.xml` 세부

- `<springProperty scope="context" name="appName" source="spring.application.name"/>` 로
  `application.yml` 값을 xml에서 참조.
- `<appender>` 를 `AsyncAppender` 로 감싸면 로깅이 애플리케이션 스레드를 덜 막음(큐 기반). 단,
  비정상 종료 시 큐에 남은 로그 유실 가능 — `neverBlock`, `queueSize` 튜닝 필요.
- `additivity="false"` : 특정 `<logger>` 의 로그가 상위(root)로 중복 전파되지 않게.
- `<shutdownHook/>` : JVM 종료 시 appender flush.

## 6. 라이브러리 로그 정리 팁

- Hibernate/JPA(이 과정은 미사용): `org.hibernate.SQL=DEBUG`, `org.hibernate.type.descriptor.sql=TRACE`
- MyBatis(Day 9~): 매퍼 인터페이스 패키지를 DEBUG로 두면 실행 SQL + 파라미터 + 결과 건수가 보임.
  `logging.level.com.example.hr.mapper=DEBUG`
- HikariCP 커넥션풀: `com.zaxxer.hikari=DEBUG` 로 풀 상태 확인(누수 디버깅 시 `leakDetectionThreshold`).
- 시끄러운 라이브러리: `logging.level.org.apache.catalina=WARN` 처럼 개별로 낮춘다.

## 7. 하지 말 것

- `System.out`/`printStackTrace()` 를 코드에 남기지 않는다(로거로 통일).
- 반복문 안에서 대량 로그 → 레벨을 TRACE로 내리고 샘플링.
- 민감정보 로깅 → 마스킹 유틸(`010-****-1234`), 또는 아예 제외. PII 규정 확인.
- 예외를 잡아서 `log.error` 만 하고 삼키기(swallow) → 상위에서 흐름을 알 수 없게 됨. 다시 던지거나
  의미 있는 처리로 이어질 때만.
