# Day 15. INDEX & EXPLAIN - 실습 답안

## 기본

### 문제 1. 인덱스 생성

```sql
CREATE INDEX IDX_BIGEMP_DEPT ON BIG_EMP (DEPT_ID);
```

**설명**: `CREATE INDEX 인덱스명 ON 테이블명 (컬럼명);` 형식입니다.

---

### 문제 2. EXPLAIN 전후 비교

**인덱스 생성 전**
```
type  key   rows
ALL   NULL  약 63000
```

**인덱스 생성 후**
```
type  key              rows
ref   IDX_BIGEMP_DEPT   약 7000
```

**설명**: 인덱스가 없을 때는 `DEPT_ID = 'D9'`인 행을 찾으려면 63,000행을 처음부터
끝까지 다 훑어야 하므로(`type = ALL`, `key = NULL`) `rows`도 전체 행 수와 비슷하게
추정됩니다. 인덱스를 만들면 `key`에 `IDX_BIGEMP_DEPT`가 나타나고 `type`이
`ref`(인덱스로 특정 값을 바로 찾는 방식)로 바뀌며, `rows`도 실제 D9 행 수 근처
(EMP 21명 중 D9는 3명이므로 63,000 × 3/21 = 약 9,000행 규모, 옵티마이저 추정치에
따라 다소 차이 가능)로 크게 줄어듭니다.

## 응용

### 문제 3. 복합 인덱스와 컬럼 순서

```sql
CREATE INDEX IDX_BIGEMP_DEPT_SALARY ON BIG_EMP (DEPT_ID, SALARY);
```

**답**: 두 번째 쿼리(`WHERE SALARY >= 3000000`, `DEPT_ID` 조건 없음)가 이 인덱스를
거의 활용하지 못합니다.

**설명**: `(DEPT_ID, SALARY)` 인덱스는 "부서 코드가 먼저, 급여가 나중"인 순서로
정렬되어 있습니다. 책의 색인이 "부서 → 급여" 순으로 정렬돼 있는 것과 같아서, 부서를
지정하지 않고 급여만으로 찾으려 하면 색인을 순서대로 훑는 이점이 사라집니다.
복합 인덱스는 반드시 **맨 앞 컬럼(DEPT_ID)부터** 조건을 걸어야 효과가 있습니다.

---

### 문제 4. 함수를 씌운 조건 다시 쓰기

```sql
SELECT * FROM BIG_EMP
WHERE HIRE_DATE BETWEEN '2013-01-01' AND '2013-12-31';
```

**설명**: `YEAR(HIRE_DATE) = 2013`은 컬럼 원본 값이 아니라 "함수를 적용한 결과"를
비교하므로 인덱스를 탈 수 없습니다. `BETWEEN`으로 2013년 1월 1일~12월 31일이라는
**컬럼 원본 값의 범위**로 바꿔 쓰면, 같은 결과를 내면서도 `HIRE_DATE` 인덱스를
그대로 활용(`type = range`)할 수 있습니다.

## 도전

### 문제 5. 타입 불일치 찾기

**답**: 첫 번째 쿼리(`WHERE EMP_ID = 200`, 따옴표 없는 숫자)가 인덱스를 타지 못합니다.

**설명**: `EMP_ID`는 `VARCHAR(3)` 문자열 타입인데 `200`(정수)과 비교하면, MySQL은
비교를 위해 내부적으로 테이블의 모든 `EMP_ID` 값을 숫자로 변환합니다. 컬럼 쪽에
이렇게 암묵적인 형변환이 걸리면 문제 4의 "컬럼에 함수를 씌운 경우"와 똑같이
인덱스를 활용할 수 없습니다. `WHERE EMP_ID = '200'`처럼 컬럼의 실제 타입(문자열)에
맞춰 비교해야 인덱스를 탈 수 있습니다.
