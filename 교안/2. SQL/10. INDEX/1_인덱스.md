# Day 15. INDEX & EXPLAIN (인덱스와 실행계획)

| 항목 | 내용 |
|---|---|
| 선수학습 | DDL(CREATE TABLE), WINDOW FUNCTION(`ROW_NUMBER`) |
| 이번 챕터 | 인덱스 개념과 구조(B+트리), 옵티마이저, `CREATE INDEX`/`DROP INDEX`, `EXPLAIN`(표·트리 형식)과 `cost` 읽는 법, 인덱스가 안 타는 경우 |
| 권장 진행 | 1일 |
| DB 기준 | MySQL 8.0 |

## 학습목표
- 인덱스가 왜 조회 속도를 높이는지 "책의 색인"에 비유해 설명하고, 실제 구조(정렬된 B+트리)를 안다.
- 옵티마이저가 무엇인지, `EXPLAIN`이 무엇을 보여주는지 설명할 수 있다.
- `CREATE INDEX`/`DROP INDEX`로 인덱스를 만들고 없애고, `SHOW INDEX`로 확인할 수 있다.
- `EXPLAIN` 결과의 `type`/`key`/`rows`(표 형식)와 `cost`/`rows`(트리 형식)를 읽고 인덱스 사용 여부·비용을 판단할 수 있다.
- 복합 인덱스에서 컬럼 순서가 왜 중요한지 설명할 수 있다.
- 인덱스를 만들어도 타지 않는 대표적인 경우(컬럼에 함수 사용, `LIKE` 앞부분 와일드카드,
  타입 불일치)를 알고 피할 수 있다.

## 1. 인덱스란

**인덱스(index)**는 책 뒤에 붙어 있는 "찾아보기(색인)"와 같습니다. 색인이 없는 책에서
특정 단어를 찾으려면 처음부터 끝까지 다 넘겨봐야 하지만(=풀 테이블 스캔), 색인이
있으면 정렬된 목록에서 바로 페이지 번호를 찾아갈 수 있습니다. `PRIMARY KEY`를 지정한
컬럼에는 MySQL이 자동으로 인덱스를 만들어주며, 그 외 컬럼은 필요할 때 `CREATE INDEX`로
직접 인덱스를 추가합니다.

> 인덱스는 조회(`SELECT`)를 빠르게 하는 대신, `INSERT`/`UPDATE`/`DELETE`할 때마다
> 인덱스도 함께 갱신해야 하므로 쓰기 성능은 떨어지고 저장 공간도 더 씁니다. "모든
> 컬럼에 인덱스를 걸면 좋다"가 아니라, **자주 조회 조건(`WHERE`, `JOIN ON`, `ORDER BY`)
> 으로 쓰이는 컬럼에만 선별적으로** 걸어야 합니다.

### 1.1 인덱스의 실제 모습 - 정렬된 B+트리

인덱스는 "색인"이라는 비유를 넘어, 실제로는 **인덱스 컬럼 값으로 정렬된 별도의
자료구조(B+트리)**가 디스크에 만들어지는 것입니다. 각 항목은
`(정렬된 컬럼 값 → 그 행을 찾아갈 위치)` 쌍이고, `SELECT`로 직접 조회하는 테이블이
아니라 옵티마이저가 뒤에서 참조만 합니다.

InnoDB에서는 한 겹 더 있습니다.

| | 구조 | 트리의 잎(leaf)에 든 것 |
|---|---|---|
| **PK 인덱스** (클러스터드 인덱스, `PRIMARY KEY` 지정 시 자동) | PK 값으로 정렬된 B+트리 | **행 전체** — 즉 테이블 본체가 곧 이 트리 |
| **보조 인덱스** (`CREATE INDEX`로 만든 것) | 그 컬럼 값으로 정렬된 B+트리 | `컬럼 값 + PK 값` |

그래서 보조 인덱스로 행을 찾으면 → 먼저 PK 값을 얻고 → **PK 인덱스에서 행 본체를 다시
찾습니다**(back-to-table). 다만 조회하려는 컬럼이 이미 보조 인덱스 안에 다 들어 있으면
이 두 번째 조회를 건너뛰는데, 이를 **커버링 인덱스**라 합니다. 이 구조가 뒤에 나오는
"스캔 종류"와 "`cost` 차이"의 바탕입니다.

- 보조 인덱스는 `키 컬럼 + PK`만 담아 테이블 본체보다 훨씬 좁음 → 인덱스 전체를 훑는
  게 테이블 전체를 훑는 것보다 쌀 수 있음
- 범위 스캔 = 이 B+트리의 잎을 **연속으로** 읽는 것 (`'곽'`으로 시작하는 구간,
  `2013-01-01 ~ 2013-12-31` 구간)

## 2. 실습용 대용량 테이블 준비 - 왜 EMP만으로는 부족한가

`EMP`는 21행뿐입니다. 이렇게 작은 테이블은 MySQL 옵티마이저가 인덱스를 타나 안 타나
체감 차이가 거의 없고, 오히려 "그냥 21행 다 읽는 게 인덱스를 거치는 것보다 빠르다"고
판단해 인덱스를 만들어도 안 쓰는 경우가 많습니다. 인덱스 효과를 눈으로 확인하려면
행이 충분히 많은 테이블이 필요하므로, `EMP`를 3,000배로 복제해 63,000행짜리
`BIG_EMP`를 만들어 실습합니다.

```sql
SET SESSION cte_max_recursion_depth = 5000;

DROP TABLE IF EXISTS BIG_EMP;

CREATE TABLE BIG_EMP AS
WITH RECURSIVE SEQ AS (
    SELECT 1 AS N
    UNION ALL
    SELECT N + 1 FROM SEQ WHERE N < 3000
)
SELECT ROW_NUMBER() OVER (ORDER BY S.N, E.EMP_ID) AS ID,
       E.EMP_NAME, E.DEPT_ID, E.JOB_CODE, E.SALARY, E.HIRE_DATE
FROM SEQ S
CROSS JOIN EMP E;

ALTER TABLE BIG_EMP ADD PRIMARY KEY (ID);

SELECT COUNT(*) FROM BIG_EMP;                              -- 63000
SELECT COUNT(*) FROM BIG_EMP WHERE EMP_NAME = '곽상혁';    -- 3000
```

**설명**: 재귀 CTE `SEQ`가 1~3000까지 숫자를 만들고, 이를 `EMP`(21행)와
`CROSS JOIN`해서 3000 × 21 = 63,000행을 만듭니다. `EMP_NAME`이 `'곽상혁'`인 행은
정확히 3,000개(`SEQ`의 숫자마다 한 번씩 복제)이므로, 이후 인덱스 유무에 따른 조회
비용 차이를 정확한 숫자로 비교할 수 있습니다. MySQL 8의 재귀 CTE는 기본적으로
1,000단계까지만 허용하므로(`cte_max_recursion_depth` 기본값 1000), 3,000단계를
반복하려면 이 세션 변수를 먼저 늘려야 합니다(`0. 환경구성`에서 다루지 않았던 시스템
변수 설정 예시이기도 합니다).

## 3. EXPLAIN으로 실행계획 보기

### 3.1 옵티마이저란

DB는 SQL을 받으면 곧바로 실행하지 않습니다. 같은 결과를 내는 여러 실행 방법(어느
인덱스를 쓸지, 조인 순서, 풀스캔 vs 인덱스 탐색)을 만들어 **각각의 예상 비용을 계산하고
가장 싼 것을 고르는** 단계가 있는데, 이를 담당하는 것이 **옵티마이저(optimizer)**입니다.
개발자는 "무엇을(What)" 구할지 SQL로 적고, "어떻게(How) 실행할지"는 옵티마이저가 정합니다.

판단에는 **통계**(인덱스별 값의 다양성, 테이블 행 수 추정치 — `ANALYZE TABLE`로 갱신)와
**비용 상수**를 씁니다. 그래서 데이터가 늘거나 통계가 바뀌면 같은 쿼리라도 실행 방법이
달라질 수 있습니다.

`EXPLAIN`은 **옵티마이저가 짠 계획을 보여주는** 명령입니다. "인덱스가 있으니 무조건 탄다"가
아니라 "옵티마이저가 그 순간 최선이라고 판단한 방식"을 보여줄 뿐입니다.

### 3.2 표 형식 EXPLAIN

```sql
EXPLAIN SELECT * FROM BIG_EMP WHERE EMP_NAME = '곽상혁';
```

**출력 결과 (주요 컬럼만)**
```
type  possible_keys  key   rows     Extra
ALL   NULL           NULL  약 63000  Using where
```

| 컬럼 | 의미 |
|---|---|
| `type` | 조회 방식. `ALL`(풀스캔) < `index` < `range` < `ref` < `eq_ref` < `const` 순으로 뒤로 갈수록 효율적 |
| `possible_keys` | 옵티마이저가 후보로 고려한 인덱스 목록 |
| `key` | 실제로 선택한 인덱스. `NULL`이면 인덱스를 전혀 안 씀 |
| `rows` | 이 단계에서 검사할 것으로 예상되는 행 수(추정치, 실제 값과 다를 수 있음) |
| `Extra` | 추가 정보(`Using where`, `Using index` 등) |

**설명**: `EMP_NAME`에 인덱스가 없으므로 `key`가 `NULL`이고, `type`이 `ALL`(63,000행을
처음부터 끝까지 훑는 풀 테이블 스캔)입니다. `rows`도 테이블 전체 행 수와 비슷하게
추정됩니다.

**`type` 값별로 무엇을 이용하나** — `range` 뒤로는 전부 **인덱스**를 쓰며, 차이는 ①
등호냐 범위냐 ② 유니크(PK/UNIQUE) 인덱스냐 아니냐 ③ 매칭 행이 1개냐 여러 개냐입니다.

| `type` | 무엇을 이용 | 언제 나오나 | 읽는 행 | 예 |
|---|---|---|---|---|
| `ALL` | 아무것도 안 씀 | 조건 컬럼에 쓸 인덱스가 없음 | 테이블 전체 | `WHERE EMP_NAME='곽상혁'` (인덱스 없을 때) |
| `index` | 인덱스 **전체**를 훑음 | 인덱스만 읽어도 답이 되거나 정렬에 쓰임 (커버링 가능) | 인덱스 전부 | `SELECT EMP_NAME FROM BIG_EMP ORDER BY EMP_NAME` |
| `range` | 인덱스의 **연속 구간** | `>` `<` `>=` `BETWEEN` `IN(...)` `LIKE 'x%'` | 구간에 든 행 | `WHERE HIRE_DATE BETWEEN '2013-01-01' AND '2013-12-31'` |
| `ref` | **비유니크** 인덱스에 **등호(`=`)** | 같은 값이 여러 행일 수 있는 인덱스 매칭 (조인 조건 포함) | 값에 맞는 여러 행 | `WHERE EMP_NAME='곽상혁'` (EMP_NAME에 일반 인덱스) |
| `eq_ref` | **PK / UNIQUE NOT NULL** 인덱스, 조인에서 | 조인 상대의 각 행마다 이 테이블에서 **정확히 1행** | 1행씩 | `EMP e JOIN DEPT d ON e.DEPT_ID=d.DEPT_ID` → `d` |
| `const` | **PK / UNIQUE** 인덱스에 **상수 등호** | 결과가 최대 1행. 시작 시 한 번 읽고 상수 취급 | 1행 | `WHERE EMP_ID='200'` (EMP_ID가 PK) |
| `system` | `const`의 특수형 | 테이블에 행이 1개뿐 | 1행 | — |

- `const` / `eq_ref` = 유니크 인덱스로 **1행** 확정 → 가장 빠름
- `ref` = 인덱스로 찾지만 유니크가 아니라 **여러 행** 가능
- `range` = 인덱스 + 범위 조건 → **구간**
- `index` = 인덱스를 **처음부터 끝까지** (그래도 테이블 전체보단 좁음)
- `ALL` = 인덱스를 **못 씀** → 테이블 전체

> 가끔 보이는 것들: `NULL`(테이블을 아예 안 읽음 — `SELECT MIN(인덱스컬럼)` 등),
> `fulltext`(`MATCH() AGAINST()`), `ref_or_null`(`col=? OR col IS NULL`),
> `index_merge`(한 테이블에서 인덱스 2개를 각각 써서 합침, 보통 `a=? OR b=?`).

트리 형식 표기와의 대응: `const`→`Constant row`, `eq_ref`→`Single-row index lookup`,
`ref`→`Index lookup`, `range`→`Index range scan`, `index`→`Index scan`(커버링이면
`Covering index scan`), `ALL`→`Table scan`.

### 3.3 트리 형식 EXPLAIN과 cost

최신 MySQL(8.0.16+)과 대부분의 DB 클라이언트는 **트리 형식**을 씁니다. 실행 순서와
**비용(`cost`)**·행 수 추정치가 함께 나옵니다.

```sql
EXPLAIN FORMAT=TREE
SELECT * FROM BIG_EMP WHERE EMP_NAME = '곽상혁';
```
```
-> Filter: (BIG_EMP.EMP_NAME = '곽상혁')  (cost=6669 rows=65966)
   -> Table scan on BIG_EMP  (cost=6669 rows=65966)
```

| 항목 | 의미 |
|---|---|
| `cost` | 옵티마이저의 **예상 비용 점수**. 밀리초가 아니라 단위 없는 숫자이며 **낮을수록 싸다**. 절대값이 아니라 대안끼리 비교하는 용도. 대략 `행 수 × 행당 평가비용 + I/O비용` |
| `rows` | 이 단계가 돌려줄 것으로 **추정한** 행 수(통계 기반, 실제와 다를 수 있음) |
| 들여쓰기 | **더 안쪽(들여쓴) 단계부터 실행**해 바깥으로 결과를 넘김 |

**EXPLAIN 종류**

| 명령 | `cost` | 쿼리 실제 실행 |
|---|---|---|
| `EXPLAIN` (표 형식) | 안 나옴 (`type`/`key`/`rows`/`filtered`) | 안 함 |
| `EXPLAIN FORMAT=TREE` | 나옴 (추정) | 안 함 |
| `EXPLAIN ANALYZE` | 추정 + `actual time=...` 실측 | **실제로 실행함** |
| `EXPLAIN FORMAT=JSON` | `query_cost` 상세 | 안 함 |

> **`EXPLAIN` 만 썼는데 표가 아니라 트리로 나온다면**: (1) DB 클라이언트가 내부적으로
> `FORMAT=TREE`로 바꿔 보내거나, (2) 서버 변수 `explain_format`(MySQL 8.0.32+)이 `TREE`로
> 설정돼 있어서입니다. `SELECT @@explain_format;` 로 확인. 형식은 `FORMAT=` 을 명시하면
> 무조건 그대로 나옵니다 — 표가 필요하면 `EXPLAIN FORMAT=TRADITIONAL SELECT ...`.

## 4. CREATE INDEX로 인덱스 생성

```sql
CREATE INDEX IDX_BIGEMP_NAME ON BIG_EMP (EMP_NAME);

EXPLAIN SELECT * FROM BIG_EMP WHERE EMP_NAME = '곽상혁';
```

**출력 결과 (주요 컬럼만)**
```
type  possible_keys      key                rows    Extra
ref   IDX_BIGEMP_NAME    IDX_BIGEMP_NAME    약 3000  Using where
```

**설명**: 인덱스를 만든 뒤에는 `key`에 `IDX_BIGEMP_NAME`이 나타나고, `type`이 `ALL`에서
`ref`(인덱스로 특정 값을 찾는 방식)로 바뀝니다. `rows`도 63,000에서 실제
`'곽상혁'`인 행 수와 같은 3,000 근처로 크게 줄어듭니다. 트리 형식으로 보면
`cost`도 `6669` → 훨씬 낮은 값으로 떨어집니다. "책 뒤의 색인에서 페이지 번호를 찾아
바로 그 페이지로 넘어가는 것"과 같은 원리입니다.

> **주의**: 옵티마이저는 **비용 기반**으로 인덱스 사용 여부를 결정합니다(3.1). 조회
> 조건에 맞는 행이 테이블의 상당 비율(예: 30% 이상)을 차지하면, 인덱스를 타는 것보다
> 그냥 풀스캔이 더 싸다고 판단해 인덱스가 있어도 `type`이 `ALL`로 나올 수 있습니다.

### 4.1 인덱스 목록 확인

만든 인덱스가 실제로 걸렸는지, 어떤 컬럼에 걸렸는지는 이렇게 확인합니다.

```sql
SHOW INDEX FROM BIG_EMP;          -- 이 테이블의 모든 인덱스
SHOW CREATE TABLE BIG_EMP;        -- CREATE 문 형태로 인덱스까지 한눈에

-- 표준 방식: 특정 컬럼에 인덱스가 있는지
SELECT INDEX_NAME, COLUMN_NAME, SEQ_IN_INDEX, NON_UNIQUE
FROM information_schema.STATISTICS
WHERE TABLE_SCHEMA = 'HR' AND TABLE_NAME = 'BIG_EMP'
ORDER BY INDEX_NAME, SEQ_IN_INDEX;
```

`SHOW INDEX` 결과에서 볼 것:

| 컬럼 | 의미 |
|---|---|
| `Key_name` | 인덱스 이름. `PRIMARY` = 기본키 인덱스 |
| `Column_name` | 인덱스에 걸린 컬럼 |
| `Seq_in_index` | 복합 인덱스에서의 컬럼 순서 (1이 선행 컬럼) |
| `Non_unique` | 0 = UNIQUE, 1 = 일반 인덱스 |
| `Cardinality` | 서로 다른 값 개수 추정치 (옵티마이저가 참고) |

특정 컬럼에 인덱스가 없으면, 범위 조건(`BETWEEN` 등)이어도 범위 스캔이 아니라
`Table scan`이 나옵니다.

## 5. 복합 인덱스(다중 컬럼 인덱스)

```sql
CREATE INDEX IDX_BIGEMP_DEPT_SALARY ON BIG_EMP (DEPT_ID, SALARY);

EXPLAIN SELECT * FROM BIG_EMP WHERE DEPT_ID = 'D9' AND SALARY >= 5000000;
EXPLAIN SELECT * FROM BIG_EMP WHERE SALARY >= 5000000;
```

**설명**: `(DEPT_ID, SALARY)` 복합 인덱스는 "부서 코드가 먼저, 급여가 나중"인 순서로
정렬됩니다. 첫 번째 쿼리(`DEPT_ID` 조건 포함)는 이 인덱스를 그대로 탈 수 있지만, 두
번째 쿼리처럼 선행 컬럼(`DEPT_ID`) 조건 없이 `SALARY`만으로 조회하면 이 인덱스를 거의
활용하지 못합니다. 책의 색인이 "부서 → 급여" 순으로 정렬돼 있는데, 부서를 지정하지
않고 급여만으로 찾으려는 것과 같기 때문입니다. 복합 인덱스는 **맨 앞 컬럼부터
순서대로** 조건을 걸어야 효과가 있습니다.

## 6. 인덱스가 안 타는 대표적인 경우

### 6.1 WHERE절 컬럼에 함수를 씌움

```sql
CREATE INDEX IDX_BIGEMP_HIRE ON BIG_EMP (HIRE_DATE);

EXPLAIN SELECT * FROM BIG_EMP WHERE YEAR(HIRE_DATE) = 2013;
-- type: ALL (HIRE_DATE에 인덱스가 있어도, YEAR()로 감싸는 순간 인덱스를 못 탐)

EXPLAIN SELECT * FROM BIG_EMP WHERE HIRE_DATE BETWEEN '2013-01-01' AND '2013-12-31';
-- type: range (HIRE_DATE 인덱스를 그대로 활용)
```

**설명**: 인덱스는 컬럼의 **원본 값**을 정렬해둔 목록입니다. `YEAR(HIRE_DATE)`처럼
컬럼에 함수를 씌우면 "함수를 적용한 결과값"은 인덱스에 없으므로, 조건에 맞는 행을
찾으려면 결국 모든 행을 하나씩 함수에 넣어봐야 합니다(풀스캔). 같은 조건이라도
`BETWEEN`처럼 컬럼 원본 값을 그대로 비교하면 인덱스를 그대로 활용할 수 있습니다.

**트리 형식으로 보면 차이가 숫자로 드러납니다.**

```
YEAR(HIRE_DATE) = 2013   (인덱스 못 탐)
-> Filter: (year(BIG_EMP.HIRE_DATE) = 2013)  (cost=6669 rows=65966)
   -> Table scan on BIG_EMP  (cost=6669 rows=65966)

HIRE_DATE BETWEEN '2013-01-01' AND '2013-12-31'   (인덱스 탐)
-> Index range scan on BIG_EMP using IDX_BIGEMP_HIRE
     over ('2013-01-01' <= HIRE_DATE <= '2013-12-31'),
     with index condition: (BIG_EMP.HIRE_DATE between '2013-01-01' and '2013-12-31')
   (cost=1350 rows=3000)
```

| 조각 | 뜻 |
|---|---|
| `Index range scan on BIG_EMP using IDX_BIGEMP_HIRE` | `HIRE_DATE` 인덱스를 범위 스캔으로 사용 |
| `over ('2013-01-01' <= HIRE_DATE <= '2013-12-31')` | 인덱스 B+트리에서 **읽을 구간의 경계** |
| `with index condition: (...)` | **인덱스 컨디션 푸시다운(ICP)**: `WHERE` 조건을 인덱스 단계에서 먼저 검사해, 안 맞는 행은 테이블 본체를 읽기 전에 걸러냄 |
| `cost=1350` (vs `6669`) | 예상 비용이 약 1/5 |
| `rows=3000` (vs `65966`) | 훑는 행이 66,000 → 3,000 |

같은 결과인데 컬럼을 함수로 감쌌는지(`YEAR(...)`) 원본을 범위로 비교했는지(`BETWEEN`)에
따라 비용이 이만큼 차이납니다.

### 6.2 LIKE 앞부분의 와일드카드

```sql
EXPLAIN SELECT * FROM BIG_EMP WHERE EMP_NAME LIKE '%상혁';   -- type: ALL
EXPLAIN SELECT * FROM BIG_EMP WHERE EMP_NAME LIKE '곽%';     -- type: range
```

**설명**: 인덱스는 문자열을 앞에서부터 정렬해둡니다. `'곽%'`처럼 **뒤쪽**에만
와일드카드가 있으면 "곽으로 시작하는 구간"을 바로 찾을 수 있지만, `'%상혁'`처럼
**앞쪽**에 와일드카드가 있으면 어디서 시작할지 알 수 없어 결국 전체를 다 훑어야
합니다.

### 6.3 타입 불일치(암묵적 형변환)

```sql
-- 참고: EMP.EMP_ID는 VARCHAR(3)
EXPLAIN SELECT * FROM EMP WHERE EMP_ID = 200;    -- 따옴표 없는 숫자 비교 -> 인덱스 활용 불가
EXPLAIN SELECT * FROM EMP WHERE EMP_ID = '200';  -- 타입을 맞춘 비교 -> 인덱스 활용 가능
```

**설명**: `EMP_ID`는 문자열 타입인데 `200`(숫자)과 비교하면, MySQL이 비교를 위해
내부적으로 모든 행의 `EMP_ID`를 숫자로 변환합니다. 컬럼 쪽에 이런 암묵적인
형변환이 걸리면 6.1절의 "함수를 씌운 경우"와 똑같이 인덱스를 탈 수 없습니다.
항상 컬럼의 실제 타입에 맞춰 비교해야 합니다.

## 7. DROP INDEX

```sql
DROP INDEX IDX_BIGEMP_NAME ON BIG_EMP;
DROP INDEX IDX_BIGEMP_DEPT_SALARY ON BIG_EMP;
DROP INDEX IDX_BIGEMP_HIRE ON BIG_EMP;

-- 실습이 끝났으면 대용량 테이블 정리
DROP TABLE BIG_EMP;
```

**설명**: 더 이상 필요 없는 인덱스는 `DROP INDEX 인덱스명 ON 테이블명;`으로
정리합니다. 이번 챕터처럼 실습용으로만 만든 대용량 테이블은 실습이 끝나면
`DROP TABLE`로 함께 정리해서 다음 챕터에 영향이 남지 않도록 합니다.

## 자주 하는 실수

- **작은 테이블에서 인덱스 효과가 없다고 "인덱스가 고장났다"고 오해** → 옵티마이저가
  비용 기반으로 정상적으로 풀스캔을 선택한 것일 수 있습니다(3.1 참고).
- **`cost` 값을 시간(ms)으로 오해** → 단위 없는 상대 점수입니다. 플랜끼리 비교할 때만
  의미가 있습니다.
- **`EXPLAIN ANALYZE`를 가볍게 실행** → 이건 추정만 하는 `EXPLAIN`과 달리 **쿼리를 실제로
  실행**합니다. `UPDATE`/`DELETE`엔 쓰지 마세요.
- **WHERE절 컬럼에 함수를 씌우고 인덱스가 안 탄다고 당황** → 컬럼 원본 값을 그대로
  비교하도록 조건을 바꿔야 합니다.
- **LIKE 앞부분에 와일드카드를 쓰고 인덱스가 안 탄다고 당황** → 구조상 불가능합니다
  (뒷부분 와일드카드만 인덱스 활용 가능).
- **컬럼과 다른 타입으로 비교(따옴표 누락 등)** → 암묵적 형변환으로 인덱스가
  무력화됩니다.
- **복합 인덱스의 뒤쪽 컬럼만으로 조회** → 선행 컬럼 조건이 없으면 인덱스를 거의
  활용하지 못합니다.
- **모든 컬럼에 인덱스를 다 걸어버림** → 쓰기 성능 저하, 저장 공간 낭비. 자주 조회
  조건으로 쓰이는 컬럼에만 선별적으로 겁니다.

## 핵심 요약

| 항목 | 핵심 내용 |
|---|---|
| 인덱스 | 정렬된 색인. `PRIMARY KEY`는 자동 생성, 그 외는 `CREATE INDEX`로 직접 추가 |
| 인덱스 구조 | 컬럼 값으로 정렬된 B+트리. InnoDB는 PK=테이블 본체(클러스터드), 보조 인덱스 잎엔 PK가 있어 back-to-table 발생(커버링이면 생략) |
| 옵티마이저 | SQL의 실행 방법을 비용 기반으로 고르는 DB 내부 단계. `EXPLAIN`은 그 결정을 보여줌 |
| `EXPLAIN` | 표 형식: `type`(ALL~const)/`key`/`rows`. 트리 형식: 실행 순서 + `cost`/`rows` |
| `cost` | 옵티마이저의 예상 비용 점수(단위 없음, 낮을수록 쌈). 트리 형식 EXPLAIN / `EXPLAIN ANALYZE`에서 확인 |
| 스캔 종류 | (싼 순) const < eq_ref < ref < range < index < ALL. 커버링이면 테이블 본체 안 읽음 |
| 인덱스 확인 | `SHOW INDEX FROM 테이블;` / `SHOW CREATE TABLE 테이블;` |
| 복합 인덱스 | 맨 앞 컬럼부터 순서대로 조건을 걸어야 효과가 있음 |
| 인덱스가 안 타는 경우 | 컬럼에 함수 사용, `LIKE '%...'` 선행 와일드카드, 타입 불일치 |
| `DROP INDEX` | `DROP INDEX 인덱스명 ON 테이블명;` |
| 트레이드오프 | 조회(SELECT)는 빨라지지만 쓰기(INSERT/UPDATE/DELETE)는 느려지고 공간을 더 씀 |
