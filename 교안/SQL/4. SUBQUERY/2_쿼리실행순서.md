# 쿼리 실행 순서 (Query Execution Order)

| 선수학습 | 이번 자료 | 권장 진행 |
|---|---|---|
| DQL(SELECT), 함수(FUNCTION), JOIN, SUBQUERY | SELECT문의 논리적 실행 순서와 그로 인해 생기는 규칙 | 1일 (4개 챕터 종합 복습과 함께) |

## 학습목표
- SELECT문이 **작성한 순서**가 아니라 정해진 **논리적 처리 순서**로 실행됨을 설명할 수
  있다.
- `FROM → ON/JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY →
  LIMIT` 순서를 각 단계가 무엇을 하는지와 함께 설명할 수 있다.
- 이 실행 순서 때문에 생기는 규칙들(별칭 사용 가능 시점, `WHERE`/`HAVING`의 차이)을
  스스로 추론해서 오류를 진단할 수 있다.
- 서브쿼리가 쓰인 위치(`WHERE`/`FROM`/`SELECT`)에 따라 언제 실행되는지 설명할 수 있다.

---

## 1. 왜 실행 순서를 알아야 하는가

지금까지 배운 `SELECT ... FROM ... WHERE ... GROUP BY ... HAVING ... ORDER BY ...
LIMIT;`은 우리가 **코드를 작성하는 순서**입니다. 그런데 MySQL이 실제로 이 문장을
**처리하는 순서**는 이것과 다릅니다. `SELECT`가 코드상 맨 위에 있어서 가장 먼저
실행될 것 같지만, 실제로는 **거의 마지막에** 처리됩니다.

이 차이를 모르면 "분명히 `SELECT`절에서 별칭을 붙였는데 왜 `WHERE`절에서는 그 별칭을
못 쓰지?" 같은 의문이 풀리지 않습니다. 지금까지 4개 챕터(DQL/함수/JOIN/SUBQUERY)에서
배운 절들을 하나로 모아, 실제 처리 순서대로 다시 정리해봅니다.

---

## 2. 논리적 실행 순서

| 순서 | 절 | 하는 일 |
|---|---|---|
| 1 | `FROM` | 조회할 테이블을 결정 |
| 2 | `ON` | `JOIN`할 때 두 테이블을 연결할 조건 적용 |
| 3 | `JOIN` | 조건에 맞춰 테이블을 결합 |
| 4 | `WHERE` | 결합된 행 중 조건에 맞는 행만 필터링 |
| 5 | `GROUP BY` | 남은 행을 지정한 기준으로 그룹화 |
| 6 | `HAVING` | 그룹화된 결과(집계값)에 조건 적용 |
| 7 | `SELECT` | 보여줄 컬럼(과 별칭)을 계산 |
| 8 | `DISTINCT` | 중복된 행 제거 |
| 9 | `ORDER BY` | 결과를 정렬 |
| 10 | `LIMIT` | 정렬된 결과 중 원하는 개수만 자르기 |

**설명**: 작성 순서(`SELECT → FROM → WHERE → GROUP BY → HAVING → ORDER BY →
LIMIT`)와 비교하면, `FROM`이 가장 먼저·`SELECT`가 거의 마지막으로 자리가 완전히
바뀝니다. "테이블에서 데이터를 가져와서(FROM) → 걸러내고(WHERE) → 묶어서(GROUP BY) →
그 묶음을 다시 거르고(HAVING) → 그제서야 어떤 컬럼을 어떻게 보여줄지 정하고(SELECT) →
정렬한다(ORDER BY)"는 흐름으로 기억하면 자연스럽습니다.

---

## 3. 한 쿼리로 단계별 확인하기

```sql
SELECT D.DEPT_TITLE, COUNT(*) AS 인원수, ROUND(AVG(E.SALARY)) AS 평균급여
FROM EMP E                                  -- 1) FROM: EMP에서 시작
JOIN DEPT D ON E.DEPT_ID = D.DEPT_ID        -- 2~3) ON/JOIN: DEPT와 결합 (DEPT_ID NULL인
                                             --    조정원·한규원은 여기서 이미 제외됨)
WHERE E.SALARY >= 2000000                   -- 4) WHERE: 결합된 19행 중 급여 조건으로 필터링
GROUP BY D.DEPT_ID, D.DEPT_TITLE            -- 5) GROUP BY: 부서별로 묶음
HAVING COUNT(*) >= 3                        -- 6) HAVING: 인원수 3명 이상인 그룹만
ORDER BY 평균급여 DESC                      -- 9) ORDER BY: SELECT 이후 실행 → 별칭(평균급여) 사용 가능
LIMIT 2;                                    -- 10) LIMIT: 정렬된 결과 중 상위 2개만
```

**출력 결과**
```
총무부      3  5900000
해외영업1부 4  2990000
```

**설명**: `FROM`~`JOIN`으로 `EMP`·`DEPT`를 결합하면 부서가 없는 조정원·한규원이 먼저
빠지고(19행), `WHERE`로 급여 200만원 미만(최주호·한재헌·심재호)이 걸러진 뒤(16행),
`GROUP BY`로 부서별 6개 그룹이 만들어집니다. `HAVING COUNT(*) >= 3`은 이 6개 그룹 중
인원 3명 이상인 총무부(3명)·해외영업1부(4명)·기술지원부(3명) 3개 그룹만 남기고,
`ORDER BY`로 평균급여 내림차순 정렬한 뒤 `LIMIT 2`로 상위 2개(기술지원부 제외)만
최종 출력됩니다.

## 4. 이 순서 때문에 생기는 규칙들

### `WHERE`에서는 `SELECT`절의 별칭을 쓸 수 없다

```sql
SELECT SALARY * 12 AS 연봉
FROM EMP
WHERE 연봉 >= 30000000;   -- 에러! Unknown column '연봉' in 'where clause'
```

`WHERE`(4번)는 `SELECT`(7번)보다 먼저 실행되므로, `WHERE`가 처리되는 시점에는 아직
`연봉`이라는 별칭이 존재하지 않습니다. 조건에는 원래 컬럼/계산식을 그대로 다시
써야 합니다.

```sql
SELECT SALARY * 12 AS 연봉
FROM EMP
WHERE SALARY * 12 >= 30000000;   -- 올바른 표현
```

### `ORDER BY`에서는 `SELECT`절의 별칭을 쓸 수 있다

```sql
SELECT SALARY * 12 AS 연봉
FROM EMP
ORDER BY 연봉 DESC;   -- OK! ORDER BY(9번)는 SELECT(7번)보다 나중에 실행됨
```

`ORDER BY`는 `SELECT`가 이미 별칭까지 계산을 끝낸 **다음**에 실행되므로, 그 별칭을
그대로 정렬 기준으로 쓸 수 있습니다.

> **MySQL의 예외**: 표준 SQL 기준으로는 `GROUP BY`(5번)도 `SELECT`(7번)보다 먼저
> 실행되므로 별칭을 쓸 수 없어야 하지만, **MySQL은 예외적으로 `GROUP BY`에서도
> `SELECT`절 별칭 사용을 허용**합니다. 다만 `WHERE`에서는 이 예외가 적용되지
> 않으므로 혼동하지 않도록 주의하세요.

### `WHERE`에는 그룹 함수를 쓸 수 없고, `HAVING`에는 쓸 수 있다

`함수(FUNCTION)` 챕터에서 이미 다룬 규칙이 바로 이 실행 순서 때문에 생깁니다.
`WHERE`(4번)가 실행되는 시점에는 아직 `GROUP BY`(5번)가 일어나지 않아 그룹 자체가
존재하지 않으므로, 그룹 함수(`SUM`, `AVG` 등)를 조건에 쓸 수 없습니다. 그룹이 만들어진
**이후**의 조건은 반드시 `HAVING`(6번)에 씁니다.

```sql
SELECT DEPT_ID, SUM(SALARY)
FROM EMP
WHERE SUM(SALARY) >= 10000000   -- 에러! 아직 그룹이 없음
GROUP BY DEPT_ID;

SELECT DEPT_ID, SUM(SALARY)
FROM EMP
GROUP BY DEPT_ID
HAVING SUM(SALARY) >= 10000000;   -- 올바른 표현
```

## 5. 서브쿼리는 어느 단계에서 실행되는가

`SUBQUERY` 챕터에서 배운 서브쿼리도, **어느 절에 놓였는지**에 따라 위 표의 해당
단계에서 실행됩니다.

| 서브쿼리 위치 | 실행되는 단계 | 예시 |
|---|---|---|
| `FROM`절 (인라인 뷰) | 1) `FROM` — 가장 먼저 실행되어 임시 테이블처럼 취급됨 | `1_SUBQUERY.md` 7절 |
| `WHERE`절 | 4) `WHERE` — 바깥 쿼리가 행을 거를 때마다 참조(상관 서브쿼리는 행마다 반복) | `1_SUBQUERY.md` 2~6절 |
| `SELECT`절 (스칼라 서브쿼리) | 7) `SELECT` — 최종 출력 직전, 행마다 값 하나를 계산해 끼워 넣음 | 아래 예시 |

`SELECT`절에도 서브쿼리를 쓸 수 있습니다. 이렇게 **값 하나만 반환**하는 서브쿼리를
**스칼라 서브쿼리(scalar subquery)**라고 부릅니다.

```sql
-- 각 사원의 급여와, 전체 평균 급여와의 차이를 함께 조회
SELECT EMP_NAME, SALARY,
       SALARY - (SELECT ROUND(AVG(SALARY)) FROM EMP) AS 평균과의차이
FROM EMP
WHERE EMP_ID IN ('200', '215');
```

**출력 결과**
```
곽상혁 8000000 4875417
한재헌 1380000 -1744583
```

**설명**: `(SELECT ROUND(AVG(SALARY)) FROM EMP)`는 전체 평균(3,124,583)을 반환하는
단일행 서브쿼리이며, `SELECT`절에서 각 행마다 실행되어 `SALARY`와의 차이를
계산합니다. 반드시 **값을 정확히 1개**만 반환해야 하며, 2개 이상 반환하면 2절에서
배운 것과 같은 `Subquery returns more than 1 row` 오류가 납니다.

---

## 자주 하는 실수

- **`SELECT`가 코드 맨 위에 있으니 가장 먼저 실행된다고 착각** → 실제로는 `FROM`이
  가장 먼저, `SELECT`는 `ORDER BY` 직전에 실행됩니다.
- **`WHERE`절에서 `SELECT`절의 별칭이나 그룹 함수를 사용하려다 오류** → `WHERE`는
  `SELECT`/`GROUP BY`보다 먼저 실행되므로 둘 다 사용할 수 없습니다.
- **집계 조건을 `HAVING`이 아니라 `WHERE`에 작성** → `WHERE`는 그룹화 전 개별 행
  조건, `HAVING`은 그룹화 후 집계 결과 조건입니다.
- **스칼라 서브쿼리가 여러 행을 반환할 수 있는 조건인지 확인하지 않음** →
  `SELECT`절 서브쿼리는 항상 값 1개만 반환해야 합니다.

---

## 핵심 요약

| 작성 순서 | 논리적 실행 순서 |
|---|---|
| ① `SELECT` | ⑦ `SELECT` |
| ② `FROM` | ① `FROM` |
| ③ `JOIN ... ON` | ②③ `ON` → `JOIN` |
| ④ `WHERE` | ④ `WHERE` |
| ⑤ `GROUP BY` | ⑤ `GROUP BY` |
| ⑥ `HAVING` | ⑥ `HAVING` |
| ⑦ `ORDER BY` | ⑨ `ORDER BY` (`DISTINCT`는 ⑧) |
| ⑧ `LIMIT` | ⑩ `LIMIT` |

**기억할 것**: `FROM`이 시작점, `SELECT`는 거의 끝. `WHERE`는 그룹화 전 조건(별칭·그룹
함수 불가), `HAVING`은 그룹화 후 조건(그룹 함수 가능). `ORDER BY`는 `SELECT` 다음이라
별칭 사용 가능. 서브쿼리는 놓인 절의 순서 그대로 실행됩니다.
