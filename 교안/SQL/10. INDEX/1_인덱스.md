# Day 15. INDEX & EXPLAIN (인덱스와 실행계획)

| 항목 | 내용 |
|---|---|
| 선수학습 | DDL(CREATE TABLE), WINDOW FUNCTION(`ROW_NUMBER`) |
| 이번 챕터 | 인덱스 개념, `CREATE INDEX`/`DROP INDEX`, `EXPLAIN` 읽는 법, 인덱스가 안 타는 경우 |
| 권장 진행 | 1일 |
| DB 기준 | MySQL 8.0 |

## 학습목표
- 인덱스가 왜 조회 속도를 높이는지 "책의 색인"에 비유해 설명할 수 있다.
- `CREATE INDEX`/`DROP INDEX`로 인덱스를 만들고 없앨 수 있다.
- `EXPLAIN` 결과의 `type`/`key`/`rows` 컬럼을 읽고 인덱스 사용 여부를 판단할 수 있다.
- 복합 인덱스에서 컬럼 순서가 왜 중요한지 설명할 수 있다.
- 인덱스를 만들어도 타지 않는 대표적인 경우(컬럼에 함수 사용, `LIKE` 앞부분 와일드카드,
  타입 불일치)를 알고 피할 수 있다.

---

## 1. 인덱스란

**인덱스(index)**는 책 뒤에 붙어 있는 "찾아보기(색인)"와 같습니다. 색인이 없는 책에서
특정 단어를 찾으려면 처음부터 끝까지 다 넘겨봐야 하지만(=풀 테이블 스캔), 색인이
있으면 정렬된 목록에서 바로 페이지 번호를 찾아갈 수 있습니다. `PRIMARY KEY`를 지정한
컬럼에는 MySQL이 자동으로 인덱스를 만들어주며, 그 외 컬럼은 필요할 때 `CREATE INDEX`로
직접 인덱스를 추가합니다.

> 인덱스는 조회(`SELECT`)를 빠르게 하는 대신, `INSERT`/`UPDATE`/`DELETE`할 때마다
> 인덱스도 함께 갱신해야 하므로 쓰기 성능은 떨어지고 저장 공간도 더 씁니다. "모든
> 컬럼에 인덱스를 걸면 좋다"가 아니라, **자주 조회 조건(`WHERE`, `JOIN ON`, `ORDER BY`)
> 으로 쓰이는 컬럼에만 선별적으로** 걸어야 합니다.

## 2. 실습용 대용량 테이블 준비 - 왜 EMP만으로는 부족한가

`EMP`는 21행뿐입니다. 이렇게 작은 테이블은 MySQL 옵티마이저가 인덱스를 타나 안 타나
체감 차이가 거의 없고, 오히려 "그냥 21행 다 읽는 게 인덱스를 거치는 것보다 빠르다"고
판단해 인덱스를 만들어도 안 쓰는 경우가 많습니다. 인덱스 효과를 눈으로 확인하려면
행이 충분히 많은 테이블이 필요하므로, `EMP`를 3,000배로 복제해 63,000행짜리
`BIG_EMP`를 만들어 실습합니다.

```sql
SET SESSION cte_max_recursion_depth = 5000;

DROP TABLE IF EXISTS BIG_EMP;

CREATE TABLE BIG_EMP AS
WITH RECURSIVE SEQ AS (
    SELECT 1 AS N
    UNION ALL
    SELECT N + 1 FROM SEQ WHERE N < 3000
)
SELECT ROW_NUMBER() OVER (ORDER BY S.N, E.EMP_ID) AS ID,
       E.EMP_NAME, E.DEPT_ID, E.JOB_CODE, E.SALARY, E.HIRE_DATE
FROM SEQ S
CROSS JOIN EMP E;

ALTER TABLE BIG_EMP ADD PRIMARY KEY (ID);

SELECT COUNT(*) FROM BIG_EMP;                              -- 63000
SELECT COUNT(*) FROM BIG_EMP WHERE EMP_NAME = '곽상혁';    -- 3000
```

**설명**: 재귀 CTE `SEQ`가 1~3000까지 숫자를 만들고, 이를 `EMP`(21행)와
`CROSS JOIN`해서 3000 × 21 = 63,000행을 만듭니다. `EMP_NAME`이 `'곽상혁'`인 행은
정확히 3,000개(`SEQ`의 숫자마다 한 번씩 복제)이므로, 이후 인덱스 유무에 따른 조회
비용 차이를 정확한 숫자로 비교할 수 있습니다. MySQL 8의 재귀 CTE는 기본적으로
1,000단계까지만 허용하므로(`cte_max_recursion_depth` 기본값 1000), 3,000단계를
반복하려면 이 세션 변수를 먼저 늘려야 합니다(`0. 환경구성`에서 다루지 않았던 시스템
변수 설정 예시이기도 합니다).

## 3. EXPLAIN으로 실행계획 보기

```sql
EXPLAIN SELECT * FROM BIG_EMP WHERE EMP_NAME = '곽상혁';
```

**출력 결과 (주요 컬럼만)**
```
type  possible_keys  key   rows     Extra
ALL   NULL           NULL  약 63000  Using where
```

| 컬럼 | 의미 |
|---|---|
| `type` | 조회 방식. `ALL`(풀스캔) < `index` < `range` < `ref` < `eq_ref` < `const` 순으로 뒤로 갈수록 효율적 |
| `possible_keys` | 옵티마이저가 후보로 고려한 인덱스 목록 |
| `key` | 실제로 선택한 인덱스. `NULL`이면 인덱스를 전혀 안 씀 |
| `rows` | 이 단계에서 검사할 것으로 예상되는 행 수(추정치, 실제 값과 다를 수 있음) |
| `Extra` | 추가 정보(`Using where`, `Using index` 등) |

**설명**: `EMP_NAME`에 인덱스가 없으므로 `key`가 `NULL`이고, `type`이 `ALL`(63,000행을
처음부터 끝까지 훑는 풀 테이블 스캔)입니다. `rows`도 테이블 전체 행 수와 비슷하게
추정됩니다.

## 4. CREATE INDEX로 인덱스 생성

```sql
CREATE INDEX IDX_BIGEMP_NAME ON BIG_EMP (EMP_NAME);

EXPLAIN SELECT * FROM BIG_EMP WHERE EMP_NAME = '곽상혁';
```

**출력 결과 (주요 컬럼만)**
```
type  possible_keys      key                rows    Extra
ref   IDX_BIGEMP_NAME    IDX_BIGEMP_NAME    약 3000  Using where
```

**설명**: 인덱스를 만든 뒤에는 `key`에 `IDX_BIGEMP_NAME`이 나타나고, `type`이 `ALL`에서
`ref`(인덱스로 특정 값을 찾는 방식)로 바뀝니다. `rows`도 63,000에서 실제
`'곽상혁'`인 행 수와 같은 3,000 근처로 크게 줄어듭니다. "책 뒤의 색인에서 페이지
번호를 찾아 바로 그 페이지로 넘어가는 것"과 같은 원리입니다.

> **주의**: MySQL 옵티마이저는 **비용 기반**으로 인덱스 사용 여부를 스스로 결정합니다.
> 조회 조건에 맞는 행이 테이블 전체의 상당 비율을 차지한다면(예: 30% 이상), 인덱스를
> 타는 것보다 그냥 풀스캔하는 게 더 빠르다고 판단해 인덱스가 있어도 `type`이 `ALL`로
> 나올 수 있습니다. `EXPLAIN`은 "인덱스가 있으니 무조건 탄다"가 아니라 "옵티마이저가
> 그 순간 최선이라고 판단한 방식"을 보여줄 뿐입니다.

## 5. 복합 인덱스(다중 컬럼 인덱스)

```sql
CREATE INDEX IDX_BIGEMP_DEPT_SALARY ON BIG_EMP (DEPT_ID, SALARY);

EXPLAIN SELECT * FROM BIG_EMP WHERE DEPT_ID = 'D9' AND SALARY >= 5000000;
EXPLAIN SELECT * FROM BIG_EMP WHERE SALARY >= 5000000;
```

**설명**: `(DEPT_ID, SALARY)` 복합 인덱스는 "부서 코드가 먼저, 급여가 나중"인 순서로
정렬됩니다. 첫 번째 쿼리(`DEPT_ID` 조건 포함)는 이 인덱스를 그대로 탈 수 있지만, 두
번째 쿼리처럼 선행 컬럼(`DEPT_ID`) 조건 없이 `SALARY`만으로 조회하면 이 인덱스를 거의
활용하지 못합니다. 책의 색인이 "부서 → 급여" 순으로 정렬돼 있는데, 부서를 지정하지
않고 급여만으로 찾으려는 것과 같기 때문입니다. 복합 인덱스는 **맨 앞 컬럼부터
순서대로** 조건을 걸어야 효과가 있습니다.

## 6. 인덱스가 안 타는 대표적인 경우

### 6.1 WHERE절 컬럼에 함수를 씌움

```sql
CREATE INDEX IDX_BIGEMP_HIRE ON BIG_EMP (HIRE_DATE);

EXPLAIN SELECT * FROM BIG_EMP WHERE YEAR(HIRE_DATE) = 2013;
-- type: ALL (HIRE_DATE에 인덱스가 있어도, YEAR()로 감싸는 순간 인덱스를 못 탐)

EXPLAIN SELECT * FROM BIG_EMP WHERE HIRE_DATE BETWEEN '2013-01-01' AND '2013-12-31';
-- type: range (HIRE_DATE 인덱스를 그대로 활용)
```

**설명**: 인덱스는 컬럼의 **원본 값**을 정렬해둔 목록입니다. `YEAR(HIRE_DATE)`처럼
컬럼에 함수를 씌우면 "함수를 적용한 결과값"은 인덱스에 없으므로, 조건에 맞는 행을
찾으려면 결국 모든 행을 하나씩 함수에 넣어봐야 합니다(풀스캔). 같은 조건이라도
`BETWEEN`처럼 컬럼 원본 값을 그대로 비교하면 인덱스를 그대로 활용할 수 있습니다.

### 6.2 LIKE 앞부분의 와일드카드

```sql
EXPLAIN SELECT * FROM BIG_EMP WHERE EMP_NAME LIKE '%상혁';   -- type: ALL
EXPLAIN SELECT * FROM BIG_EMP WHERE EMP_NAME LIKE '곽%';     -- type: range
```

**설명**: 인덱스는 문자열을 앞에서부터 정렬해둡니다. `'곽%'`처럼 **뒤쪽**에만
와일드카드가 있으면 "곽으로 시작하는 구간"을 바로 찾을 수 있지만, `'%상혁'`처럼
**앞쪽**에 와일드카드가 있으면 어디서 시작할지 알 수 없어 결국 전체를 다 훑어야
합니다.

### 6.3 타입 불일치(암묵적 형변환)

```sql
-- 참고: EMP.EMP_ID는 VARCHAR(3)
EXPLAIN SELECT * FROM EMP WHERE EMP_ID = 200;    -- 따옴표 없는 숫자 비교 -> 인덱스 활용 불가
EXPLAIN SELECT * FROM EMP WHERE EMP_ID = '200';  -- 타입을 맞춘 비교 -> 인덱스 활용 가능
```

**설명**: `EMP_ID`는 문자열 타입인데 `200`(숫자)과 비교하면, MySQL이 비교를 위해
내부적으로 모든 행의 `EMP_ID`를 숫자로 변환합니다. 컬럼 쪽에 이런 암묵적인
형변환이 걸리면 6.1절의 "함수를 씌운 경우"와 똑같이 인덱스를 탈 수 없습니다.
항상 컬럼의 실제 타입에 맞춰 비교해야 합니다.

## 7. DROP INDEX

```sql
DROP INDEX IDX_BIGEMP_NAME ON BIG_EMP;
DROP INDEX IDX_BIGEMP_DEPT_SALARY ON BIG_EMP;
DROP INDEX IDX_BIGEMP_HIRE ON BIG_EMP;

-- 실습이 끝났으면 대용량 테이블 정리
DROP TABLE BIG_EMP;
```

**설명**: 더 이상 필요 없는 인덱스는 `DROP INDEX 인덱스명 ON 테이블명;`으로
정리합니다. 이번 챕터처럼 실습용으로만 만든 대용량 테이블은 실습이 끝나면
`DROP TABLE`로 함께 정리해서 다음 챕터에 영향이 남지 않도록 합니다.

## 자주 하는 실수

- **작은 테이블에서 인덱스 효과가 없다고 "인덱스가 고장났다"고 오해** → 옵티마이저가
  비용 기반으로 정상적으로 풀스캔을 선택한 것일 수 있습니다(2절 참고).
- **WHERE절 컬럼에 함수를 씌우고 인덱스가 안 탄다고 당황** → 컬럼 원본 값을 그대로
  비교하도록 조건을 바꿔야 합니다.
- **LIKE 앞부분에 와일드카드를 쓰고 인덱스가 안 탄다고 당황** → 구조상 불가능합니다
  (뒷부분 와일드카드만 인덱스 활용 가능).
- **컬럼과 다른 타입으로 비교(따옴표 누락 등)** → 암묵적 형변환으로 인덱스가
  무력화됩니다.
- **복합 인덱스의 뒤쪽 컬럼만으로 조회** → 선행 컬럼 조건이 없으면 인덱스를 거의
  활용하지 못합니다.
- **모든 컬럼에 인덱스를 다 걸어버림** → 쓰기 성능 저하, 저장 공간 낭비. 자주 조회
  조건으로 쓰이는 컬럼에만 선별적으로 겁니다.

## 핵심 요약

| 항목 | 핵심 내용 |
|---|---|
| 인덱스 | 정렬된 색인. `PRIMARY KEY`는 자동 생성, 그 외는 `CREATE INDEX`로 직접 추가 |
| `EXPLAIN` | `type`(ALL~const), `key`(사용한 인덱스), `rows`(예상 검사 행 수)로 실행계획 확인 |
| 복합 인덱스 | 맨 앞 컬럼부터 순서대로 조건을 걸어야 효과가 있음 |
| 인덱스가 안 타는 경우 | 컬럼에 함수 사용, `LIKE '%...'` 선행 와일드카드, 타입 불일치 |
| `DROP INDEX` | `DROP INDEX 인덱스명 ON 테이블명;` |
| 트레이드오프 | 조회(SELECT)는 빨라지지만 쓰기(INSERT/UPDATE/DELETE)는 느려지고 공간을 더 씀 |
