# 0. 데이터 타입 (MySQL)

| 항목 | 내용 |
|---|---|
| 이번 자료 | `CREATE TABLE`에서 컬럼마다 지정하는 데이터 타입의 의미와 선택 기준 |
| 권장 시점 | `02_실습데이터.md`의 `CREATE TABLE` 스크립트를 읽기 전 |

## 학습목표
- 문자형(`CHAR`/`VARCHAR`), 숫자형(`INT`/`DECIMAL`), 날짜형(`DATE`/`DATETIME`) 데이터
  타입의 차이를 설명할 수 있다.
- 저장할 값의 성격에 맞는 데이터 타입을 스스로 고를 수 있다.
- `02_실습데이터.md`의 `EMP`/`DEPT` 등 테이블 정의에서 각 컬럼에 그 타입을 쓴 이유를
  설명할 수 있다.

---

## 1. 데이터 타입이 왜 중요한가

`CREATE TABLE`로 테이블을 만들 때는 컬럼마다 **어떤 종류의 값을 담을지**를 반드시
지정해야 합니다.

```sql
CREATE TABLE EMP (
    EMP_ID   VARCHAR(3),
    SALARY   INT,
    HIRE_DATE DATE
);
```

데이터 타입을 정하는 것은 단순한 형식이 아니라 세 가지 실질적인 이유가 있습니다.

1. **저장 공간**: 타입마다 차지하는 저장 공간이 다릅니다. `INT`는 항상 4바이트지만,
   `CHAR(2)`는 2바이트만 차지합니다. 불필요하게 큰 타입을 쓰면 공간이 낭비됩니다.
2. **연산 가능 여부**: `SALARY`처럼 숫자 타입이어야 `SUM`, `AVG`, `>=` 같은 산술/비교
   연산이 가능합니다. 숫자를 문자로 저장하면 `'8000000' + 1`처럼 매번 형변환 문제가
   생깁니다.
3. **데이터 무결성**: `HIRE_DATE`를 `DATE` 타입으로 선언해두면 `'2013-13-45'`처럼
   말이 안 되는 날짜는 애초에 저장 자체가 거부됩니다. 문자열로 저장했다면 이런 오류를
   DB가 막아주지 못합니다.

---

## 2. 문자형 — CHAR vs VARCHAR

| 타입 | 특징 |
|---|---|
| `CHAR(n)` | **고정 길이**. 항상 n자리를 차지하며, 실제 값이 짧으면 뒤에 공백을 채워 저장 |
| `VARCHAR(n)` | **가변 길이**. 실제 값의 길이만큼만 저장(최대 n자까지) |

우리 실습 스키마의 `DEPT` 테이블로 비교해봅시다.

```sql
CREATE TABLE DEPT (
    DEPT_ID     CHAR(2),      -- 'D1', 'D9' ...
    DEPT_TITLE  VARCHAR(35),  -- '인사관리부', '해외영업1부' ...
    LOCATION_ID CHAR(2)
);
```

- **`DEPT_ID CHAR(2)`**: 부서코드는 `'D1'`~`'D9'`처럼 **항상 정확히 2글자**입니다.
  길이가 고정되어 있으므로 `CHAR`가 적합합니다.
- **`DEPT_TITLE VARCHAR(35)`**: 부서명은 `'총무부'`(3글자)부터 `'해외영업1부'`(6글자)까지
  **길이가 제각각**입니다. 이런 값은 `VARCHAR`로 선언해서 실제 글자 수만큼만 저장하는
  것이 공간을 아낍니다.

> **참고**: `EMP_ID`는 `'200'`처럼 숫자로만 이루어져 있지만 `VARCHAR(3)`로 선언되어
> 있습니다. 사번은 **더하거나 빼는 연산을 하지 않는 식별자**이고, 앞으로 `'A01'`처럼
> 문자가 섞인 사번 체계로 바뀔 수도 있으므로 처음부터 숫자 타입이 아니라 문자 타입으로
> 설계한 것입니다. "숫자처럼 보인다고 무조건 숫자 타입은 아니다"를 보여주는 대표적인
> 예시입니다.

## 3. 숫자형 — INT vs DECIMAL

| 타입 | 특징 |
|---|---|
| `INT` | 정수만 저장(소수점 없음). 약 -21억 ~ +21억까지 표현 가능 |
| `DECIMAL(전체자릿수, 소수점이하자릿수)` | 정확한 소수를 저장(금액·비율 등 오차가 있으면 안 되는 값) |

```sql
SALARY  INT,            -- 8000000
BONUS   DECIMAL(4, 2)   -- 0.30, 0.15 ...
```

- **`SALARY INT`**: 급여는 항상 정수(원 단위)이므로 `INT`면 충분합니다.
- **`BONUS DECIMAL(4, 2)`**: `DECIMAL(4, 2)`는 "전체 4자리 중 소수점 아래 2자리"라는
  뜻으로, `-99.99`~`99.99` 범위를 정확하게 표현합니다. 보너스율(`0.30`, `0.15` 등)처럼
  **소수점 계산이 정확해야 하는 값**은 부동소수점 오차가 있는 `FLOAT`/`DOUBLE`이 아니라
  `DECIMAL`을 씁니다.

> **왜 `FLOAT`을 쓰지 않나요?** `FLOAT`/`DOUBLE`은 내부적으로 이진수로 근사 저장되기
> 때문에 `0.1 + 0.2`가 `0.3`이 정확히 나오지 않는 등 미세한 오차가 생길 수 있습니다.
> 급여·보너스·가격처럼 **1원 단위의 오차도 허용되지 않는 값**은 항상 `DECIMAL`을
> 사용합니다.

## 4. 날짜/시간형 — DATE vs DATETIME

| 타입 | 저장되는 값 | 예시 |
|---|---|---|
| `DATE` | 날짜만 (연-월-일) | `2013-03-02` |
| `DATETIME` | 날짜 + 시각 | `2013-03-02 09:00:00` |
| `TIMESTAMP` | 날짜 + 시각(시간대 정보 포함, 자동 갱신 등에 사용) | `2013-03-02 09:00:00` |

```sql
HIRE_DATE DATE,   -- 입사"일자"만 필요 (몇 시에 입사했는지는 의미 없음)
ENT_DATE  DATE
```

`HIRE_DATE`, `ENT_DATE`는 "몇 시에 입사/퇴사했는지"가 아니라 "**며칠에**"만 의미가
있으므로 `DATE`로 충분합니다. 로그 기록처럼 정확한 시각까지 필요하다면
`DATETIME`이나 `TIMESTAMP`를 사용합니다.

## 5. 우리 실습 스키마 정리

`EMP` 테이블의 각 컬럼이 왜 그 타입인지 표로 정리하면 다음과 같습니다.

| 컬럼 | 타입 | 선택 이유 |
|---|---|---|
| `EMP_ID` | `VARCHAR(3)` | 연산하지 않는 식별자, 향후 문자 포함 가능성 |
| `EMP_NAME` | `VARCHAR(20)` | 이름 길이가 사람마다 다름 |
| `EMP_NO` | `CHAR(14)` | 주민등록번호 형식(`'800514-1234567'`)은 **항상 14글자로 고정** |
| `EMAIL` | `VARCHAR(25)` | 길이가 제각각 |
| `PHONE` | `VARCHAR(12)` | 길이가 제각각(자릿수 다른 번호 포함 가능) |
| `DEPT_ID`, `JOB_CODE` | `CHAR(2)` | 항상 2글자로 고정된 코드 |
| `SALARY` | `INT` | 정수 금액 |
| `BONUS` | `DECIMAL(4, 2)` | 정확한 소수(비율) |
| `MANAGER_ID` | `VARCHAR(3)` | `EMP_ID`를 그대로 참조하는 FK이므로 같은 타입 |
| `HIRE_DATE`, `ENT_DATE` | `DATE` | 날짜만 필요 |
| `ENT_YN` | `CHAR(1)` | `'Y'`/`'N'` 중 하나, 항상 1글자 |

> **FK와 참조하는 PK는 타입이 반드시 같아야 합니다.** `EMP.DEPT_ID CHAR(2)`는
> `DEPT.DEPT_ID CHAR(2)`를 참조하므로 두 컬럼의 타입(과 길이)이 정확히 일치합니다.
> `MANAGER_ID VARCHAR(3)`도 마찬가지로 `EMP.EMP_ID VARCHAR(3)`과 타입을 맞췄습니다.

## 자주 하는 실수

- **모든 문자열을 습관적으로 `VARCHAR`로만 선언** → `DEPT_ID`, `JOB_CODE`처럼 길이가
  항상 고정된 코드값은 `CHAR`가 더 적합합니다. `CHAR`는 길이 비교/인덱싱이 살짝 더
  빠르다는 실무적 이유도 있습니다.
- **금액/비율에 `FLOAT`을 사용** → 부동소수점 오차 때문에 정확한 값이 보장되지
  않습니다. 반드시 `DECIMAL`을 사용하세요.
- **저장할 최댓값보다 짧게 길이를 잡음** → `VARCHAR(10)`짜리 컬럼에 11글자를
  `INSERT`하면 오류가 나거나(엄격 모드) 잘려서 저장됩니다. 여유 있게 길이를 잡되,
  근거 없이 너무 크게 잡지도 않습니다.
- **FK 컬럼과 참조 대상 PK 컬럼의 타입/길이를 다르게 설정** → `CHAR(2)`와
  `VARCHAR(2)`처럼 타입이 다르면 `FOREIGN KEY` 제약을 걸 수 없거나, `JOIN` 시
  예상과 다른 결과가 나올 수 있습니다.

## 핵심 요약

| 구분 | 타입 | 언제 쓰는가 |
|---|---|---|
| 문자(고정 길이) | `CHAR(n)` | 코드값처럼 길이가 항상 같음 (`DEPT_ID`, `JOB_CODE`) |
| 문자(가변 길이) | `VARCHAR(n)` | 이름/이메일처럼 길이가 제각각 |
| 정수 | `INT` | 소수점이 필요 없는 값 (`SALARY`) |
| 정확한 소수 | `DECIMAL(전체, 소수)` | 금액·비율처럼 오차가 있으면 안 되는 값 (`BONUS`) |
| 날짜만 | `DATE` | 시각이 의미 없는 값 (`HIRE_DATE`) |
| 날짜+시각 | `DATETIME`/`TIMESTAMP` | 정확한 시각까지 필요한 값 |
